# Дизайн: единицы скорости

## Context

Мотивация — в [proposal.md](proposal.md), требования — в
[specs/display-units/spec.md](specs/display-units/spec.md).

Как устроено сейчас:

- Данные машин Iron Horse (`web/src/data/trains.json`) хранят только `speed_mph` — значение,
  которое дизайнер ростера пишет в NML (`properties.pynml`: `speed: ${...}mph`). Внутренней
  скорости в этих данных нет.
- Ванильные данные (`vanilla_trains.json`) уже хранят и `speed_mph`, и `speed_internal`
  (`rvi["max_speed"]` — ровно то, чем оперирует игра), но `web/src/vanilla.ts` пробрасывает в
  веб-слой только `speed_mph`.
- Движок считает физику во внутренних единицах: `engine/physics.ts` возвращает установившуюся
  скорость в них, а `engine/consist.ts` и `engine/optimize.ts` на выходе конвертируют её в mph
  (`internalToMph`) и отдают UI поля `*Mph`.
- Скорость выводится в четырёх местах: колонка каталога и три показателя состава в
  `features/consist/ConsistPage.tsx`, два столбца в `features/optimizer/OptimizerPage.tsx`,
  два места в `features/route/RoutePage.tsx`. Единица подставляется строкой `t('units.mph')`.
- Настройки отображения (язык, валюта) стоят в блоке `settings.display` на вкладке настроек;
  валюта живёт в `state/settingsStore.ts` рядом с `game`/`calc`, формат денег — `money()` в
  `components/format.ts`, читающая стор вне React.

Ограничение, определяющее подход: игра считает отображаемую скорость из внутренней единицы
(`strings.cpp`, `ConvertKmhishSpeedToDisplaySpeed` = `ToDisplay(speed * 10, false) / 16`, где
`ToDisplay` усекает, а не округляет). Перевод «mph → км/ч» поверх уже округлённого mph теряет
информацию: у 112 mph Iron Horse он даёт 180 вместо 181, которые показывает игра.

## Goals / Non-Goals

**Goals:**

- Отображаемая скорость (в обеих системах) считается из внутренней единицы игры одной функцией.
- Движок не знает о выбранной системе единиц: он отдаёт внутренние единицы, UI форматирует.
- Внутренняя скорость машины приходит из данных, а не восстанавливается в вебе.

**Non-Goals:**

- Не меняем `mphToInternal()` и вход физики: числа расчёта должны остаться прежними
  (см. Risks — расхождение на 1 внутреннюю единицу у быстрых машин остаётся как было).
- Не трогаем единицы мощности, веса, длины и денег.
- Не вводим общий «формат величины»: скорость получает свою функцию форматирования рядом с
  `money()`, обобщение — по мере надобности.

## Decisions

### 1. Настройка живёт в `settingsStore` рядом с валютой, а не в `GameSettings`/`CalcSettings`

Поле `speedUnit: 'imperial' | 'metric'` кладём в `state/settingsStore.ts` верхним уровнем,
как `currency`; значение по умолчанию `'metric'`, `reset()` возвращает его же.

Правило проекта «каждая настройка обязана менять расчёт» относится к `GameSettings` и
`CalcSettings` (его сторожит `engine/__tests__/settings-effect.test.ts`), а единица отображения
расчёт не меняет — значит ей там не место. Отдельный стор (как `localeStore`) тоже не нужен:
валюта — настройка того же класса и уже лежит в `settingsStore`, ставим соседним полем, чтобы
блок «Отображение» собирался из одного места.

Миграция persist не нужна: `merge` в сторе строит состояние как `{...current, ...persisted}`,
поэтому у сохранённых настроек без этого поля возьмётся значение по умолчанию. Версию стора
(`version: 1`) не трогаем — старые данные остаются валидными.

Альтернатива — положить в `CalcSettings`: отклонена, сломала бы `settings-effect.test.ts`
(настройка не влияет ни на одно число) и потребовала бы исключений в тесте.

### 2. Конверсия — в `engine/units.ts`, по формуле игры

Добавляем `internalToKmh(internal)`: `Math.floor(Math.trunc(internal * 10 * 1.609344) / 16)` —
буквальный перенос `UnitConversion::ToDisplay(input, round = false)` с последующим целочисленным
делением на 16 (`strings.cpp`). Существующая `internalToMph` — тот же путь с множителем 1.0.

Альтернатива — множитель NML (`ottd_mul = 103`, `ottd_shift = 6`, то есть 1.609375): на текущем
наборе скоростей даёт те же числа, но это приближение компилятора GRF, а показывает скорость
игра. Берём константу игры.

### 3. Внутреннюю скорость Iron Horse пишет экстрактор, а не веб

`pipeline/extract_iron_horse.py` добавляет к машине `speed_internal` (и `speed_lgv_internal` для
LGV-скорости), повторяя то, что делает NML при компиляции свойства 0x09
(`nml/actions/action0properties.py`): `n = round(mph * 1.6)` (перевод mph → м/с → внутренние
единицы сокращается до 5000/3125), затем `n` подправляется на ±1, пока `(10 * n) // 16` не
станет равно исходному mph. Именно это число попадает в GRF, и
именно им оперирует игра, когда показывает скорость.

Так же это соответствует правилу проекта: данные о машинах меняются только через экстракторы и
`make data`, JSON руками не правятся. Ванильный экстрактор уже пишет `speed_internal` — правки
там не нужны, поле надо лишь пробросить через `web/src/types.ts` и `web/src/vanilla.ts`.

`speed_mph` остаётся в данных: он и первичен для Iron Horse (дизайнер задаёт mph), и используется
существующей логикой (`consist.ts`, тесты, `vanilla.test.ts`).

Альтернатива — считать внутреннюю скорость в TypeScript из `speed_mph`: результат тот же, но
знание о том, как NML записывает свойство, — часть извлечения данных, а не игровой формулы, и
в вебе оно оказалось бы вторым источником правды.

### 4. Движок отдаёт внутренние единицы, форматирует UI

`engine/consist.ts` и `engine/optimize.ts` меняют выходные поля с `*Mph` на `*Internal`
(`balancingSpeedInternal`, `balancingSpeedOnGradeInternal`, `speedLimitInternal`,
`loadedSpeedInternal`, `emptySpeedInternal`, `gradeSpeedInternal`). Это убирает двойное
округление (internal → mph → км/ч) и оставляет выбор единицы UI-слою.

`speedLimitInternal` собирается как минимум `speed_internal` по машинам состава — то есть из
данных, чтобы показанный предел совпадал с игрой. Вход физики (`maxSpeedInternal`) остаётся
прежним — `mphToInternal(speedLimit)`, — чтобы числа расчёта не изменились (см. Risks).

Затронутые модули `engine/`: `units.ts` (новая конверсия), `consist.ts` и `optimize.ts`
(тип результата), `physics.ts` — без изменений. Настройки `GameSettings`/`CalcSettings` в этом
изменении не участвуют.

### 5. Форматирование — `speed()` в `components/format.ts`

Функция `speed(internal)` возвращает строку «181 км/ч» / «112 mph»: выбирает конверсию по
`speedUnit` из стора и подставляет `t('units.kmh')` или `t('units.mph')`. Читает стор через
`getState()`, как `money()`; перерисовку обеспечивают страницы, уже подписанные на
`useSettingsStore()`, а строки скорости собираются в момент рендера (в `render` колонок и в
JSX), а не внутри `useMemo` — как того требует правило локализации.

### 6. Строки интерфейса — из локали игры

Русские подписи берём из `vendor/openttd/src/lang/russian.txt`, английские — из `english.txt`:
настройка «Система единиц скорости наземных ТС» / «Speed units (land)», подсказка «Показывать
значения скорости в выбранной системе единиц», варианты «английская (миль/ч)» / «Imperial (mph)»
и «метрическая (км/ч)» / «Metric (km/h)», единица «км/ч» / «km/h».

## Risks / Trade-offs

- **Смена того, что видят текущие пользователи** (по умолчанию км/ч вместо миль/ч) → выбор
  сделан осознанно: калькулятор должен показывать то же, что игра со стандартными настройками.
  Переключатель стоит на видном месте рядом с валютой, запись идёт в CHANGELOG.
- **Предел скорости из данных против предела в физике**: `mphToInternal()` округляет
  `mph × 1.6` и у быстрых машин даёт на единицу меньше настоящей внутренней скорости
  (112 mph → 179 против 180). Показанное «Ограничение скорости» будет из данных (совпадает с
  игрой), а установившаяся скорость по-прежнему упирается в число физики. Расхождение
  существует и сегодня (в mph: предел 112, установившаяся не выше 111) — оно не создаётся этим
  изменением, и чинить его здесь нельзя: это изменит числа расчёта. Отдельная задача.
- **Перегенерация данных**: `make data` переписывает JSON целиком → перед коммитом убедиться,
  что в diff `trains.json` только новые поля скорости.
- **Переименование полей результата движка** затронет тесты (`engine.test.ts`,
  `settings-effect.test.ts` читает `loadedSpeedMph`/`gradeSpeedMph`) → правится в том же шаге,
  что и сами поля.

## Migration Plan

Миграции нет: persist-версия стора не меняется, недостающее поле подставляется значением по
умолчанию при загрузке. Откат — обратный коммит; сохранённые настройки от него не страдают,
лишнее поле в localStorage просто игнорируется.
