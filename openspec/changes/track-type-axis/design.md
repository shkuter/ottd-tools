# Design: track-type-axis

## Context

Мотивация — в proposal.md; требования — в спеках change. Технически сейчас:

- `calc.trackType: TrackType` (`engine/settings.ts:236`, союз в `types.ts:12`) — семейство
  `'RAIL'|'NG'|'METRO'|'MONO'|'MAGLEV'`; фильтры в `optimize.ts:294,303` — точное равенство
  `base_track_type === trackType`.
- `allowElectric` — **не URL-параметр, а поле persist-стора**: `state/searchParams.ts:10-23`
  (`DEFAULT_SEARCH_PARAMS`, `searchStorePersist()` `:41-56`, `SEARCH_STORE_VERSION = 1`).
  Второй, независимый экземпляр — у вкладки снабжения (`state/industrySupplyStore.ts:54`,
  контрол `features/industry-supply/IndustrySupplyPage.tsx:137`, прокидывание в
  `features/industry-supply/inputs.ts:16,92`). `URLSearchParams` в `web/src` не используется
  вовсе. Отсекает `isPureElectric()` (`optimize.ts:82`).
- В `trains.json` у каждой из 1648 машин есть `base_track_type`, `track_types` (лейблы),
  `lgv_capable`, `speed_lgv_mph/_internal` и `power_by_source` — **мапа «источник → л.с.»**
  (`{"DIESEL":950,"OHLE":2500}` у `shoebox`; 13 машин с двумя источниками, 21 с
  `lgv_capable`). Из них читается только `power_by_source` — и только в `isPureElectric`.
- В `vanilla_trains.json` — сырой макрос `railtype: 'R'|'C'|'O'|'L'`
  (`extract_vanilla.py:223`); `vanilla.ts:69-74` схлопывает `C` (ELECTRIC) в `'RAIL'`.
- Таблиц самих railtype (лимит, powered/compatible, имя) в данных нет вообще.
- `settingsStore` — persist версии 2 с ветками лесенкой (`version < 1`, `< 2`), новая ветка
  ложится штатно.

Семантика отношений в источниках: маски хранятся **со стороны типа машины**
(`vendor/openttd/src/rail.h:176-181`). Важная тонкость: в NewGRF списки перечисляют
**другие** типы — свой подразумевается и в списке не пишется (`narrow_gauge.py` объявляет
powered `["NAAE"]`, у `metro.py` списки пусты), тогда как ванильная таблица включает свой
тип явно (`railtypes.h:65`: RAIL powered = {RAIL, ELECTRIC}). Приведение к одному виду —
задача экстрактора, см. D1.

## Goals / Non-Goals

**Goals:**

- Таблица railtype в данных каждого набора; выбор пути — лейбл railtype, а не семейство.
- Допуск и числа машин зависят от выбранного пути (powered/compatible, лимит, LGV, мощность
  по источнику тяги).
- Миграции сохранённого состояния во всех трёх сторах без потери смысла выбора.

**Non-Goals:**

- Не менять модель `base_track_type` в данных: семейство остаётся (скорости/вместимости
  Iron Horse заданы по нему, `purchaseKey()` `purchase.ts:24-27` группирует по нему).
- Не трогать физику разгона как таковую — меняются только входы (предел скорости, мощность).

## Decisions

### D1. Таблица railtype живёт в данных своего набора, маски нормализованы

`trains.json.meta.railtypes` (пишет `extract_iron_horse.py`) и
`vanilla_trains.json.meta.railtypes` (пишет `extract_vanilla.py`); `dataset.ts` отдаёт
таблицу активного набора рядом с `activeTrains()`. Запись:

```
{ label, name, speed_limit_internal,        // 0 = нет лимита
  powered: [label...], compatible: [label...],  // со стороны типа машины, СО СВОИМ типом
  lgv: bool, sort }
```

Альтернатива — отдельный `railtypes.json` — отклонена: два экстрактора писали бы в один
файл, и файл пришлось бы согласовывать с включённым набором отдельным кодом.

**Нормализация масок — обязательна, иначе каталог пустеет.** Экстрактор Iron Horse:
(1) отбрасывает legacy-лейблы, которых нет в собственной таблице (`NAAE`, `IHA_`, `IHB_`,
`IHBA`); (2) **добавляет сам тип** в обе маски. Без второго шага у `NAAN` и `MTRO` маски
станут пустыми и по формуле D2 ни одна узкоколейная машина и ни один поезд метро не
окажутся допущены на свой же путь. Ванильные маски уже включают свой тип — приводим к
одному виду. Тест пайплайна: у каждого типа его собственный лейбл входит в `powered` и в
`compatible`, и все ссылки масок разрешаются в таблице.

Прочие частности данных:

- Ваниль: лейблы из `rail_type.h:17-20` (`RAIL`, `ELRL`, `MONO`, **`MGLV`** — не `MAGLEV`,
  это имя семейства), маски и `max_speed` из `table/railtypes.h`. `extract_vanilla.py`
  декодирует макрос `p[9]` в лейбл у себя (как уже декодирует `RUNNING_COST_KEYS` и
  `ENGINE_CLASS_KEYS`), наружу сырая буква не выходит, и `vanilla.ts` теряет свой маппинг.
- Iron Horse: 6 типов из `src/railtypes/*.py`. У `rail` и `rail_electrified_ohle`
  `suppress_for_nml=True` (их определяет игра) и `sort_order = None` — маски и порядок для
  них берутся ванильные. `speed_limit` есть у всех (`railtype.py:17`, по умолчанию 0).

### D2. Допуск машины считается в рантайме по таблице, а не прекомпилируется в машины

Новый чистый модуль `engine/tracktypes.ts`:

- `isPoweredOn(train, railtype, table)` — существует ли `L ∈ train.track_types`, для
  которого `railtype.label ∈ table[L].powered`; `isCompatibleWith` — то же по `compatible`.
  Работает благодаря нормализации D1: у машины на своём же пути отношение выполняется.
- `vehicleSpeedOn(train, railtype)` — `speed_lgv_internal` на `lgv`-пути для
  `lgv_capable`-машин, иначе `speed_internal`; предел состава затем
  `min(..., railtype.speed_limit_internal || ∞)`.
- `vehiclePowerOn(train, railtype)` — мощность по источнику тяги, доступному на пути.

Альтернатива — экстрактор пишет каждой машине готовые `powered_on: [...]` — отклонена:
раздувает 1648 записей данными, выводимыми из таблицы в шесть строк.

Электро-дизель проходит без спецкейса: `track_types = [ELRL, RAIL]`, и `RAIL ∈
powered(RAIL)` даёт допуск на обычный путь, а мощность решает `vehiclePowerOn`.

### D3. Мощность по источнику тяги — из готовой мапы `power_by_source`

`power_by_source` уже лежит в данных мапой «источник → л.с.» (проверено, см. Context) —
извлекать нечего, правок экстрактора не нужно. Правило выбора: на электрифицированном пути
— значение `OHLE`, иначе — максимум неэлектрических источников. У ванили источник один,
ничего не меняется. Источник в Iron Horse — `schemas.py:509-511`
(`power_by_power_source`), дерево переключателей мощности — `:650-684`.

### D4. Выбор — `calc.trackType` с доменом лейблов; мигрируют три стора

`CalcSettings.trackType: string` (лейбл railtype), дефолт `'RAIL'`. Участвует в расчёте —
кейс в `settings-effect.test.ts:195` перестраивается с `'NG'` на пару, различимую только
машинами (`RAIL` против `ELRL`); механизм собственной базы кейса (`base`/`baseCalc`,
`:114`) уже есть. `GameSettings` не трогается.

Миграция семейства в лейбл — обычная ветка `settingsStore` (v2 → v3, лесенкой, ранний
выход по текущей версии, тест на состояние каждой прошлой версии): `NG → NAAN`,
`METRO → MTRO`, `MAGLEV → MGLV`; `RAIL` и `MONO` остаются собой.

Перенос флажка сложнее: он сохранён в двух чужих сторах, а выбор пути — один, и **порядок
гидратации сторов не определён** — его задаёт порядок импорта модулей. Миграция внутри
`settingsStore` здесь не годится: если стор вкладки гидратируется первым и перепишет свой
ключ без поля `allowElectric`, переносить будет уже нечего, и пользователь молча потеряет
электрификацию. Решение — **одноразовый шаг апгрейда вне сторов**, выполняемый в точке
входа до их создания: он читает три сырых ключа `localStorage` (ключи известны, у каждого
внутри `state` и `version`), при `trackType === 'RAIL'` и любом сохранённом
`allowElectric === true` записывает выбор `ELRL`, вычищает поля флажка из чужих ключей и
помечает себя выполненным. Приоритет у стора оптимизатора: это вкладка, ради которой
флажок заводился. Сами сторы вкладок поле просто перестают объявлять — их собственные
миграции о флажке ничего не знают, поэтому порядок гидратации перестаёт что-либо решать.

Альтернативы: делать перенос в `migrate` самого `settingsStore` — отклонена по причине
выше (гонка порядка); спросить пользователя баннером — отклонена: у прежнего выбора есть
однозначный смысл, и молчаливый перенос честнее вопроса «чего вы хотели».

### D5. Контрол один, экземпляров четыре

Компонент `TrackTypeSelect` (features), читает/пишет `settingsStore.calc.trackType`,
ставится в ряд отбора **четырёх** вкладок — подбор, конструктор состава, доход рейса,
снабжение — и в Settings. Локальный `useState`-фильтр `ConsistPage.tsx:57` и оба флажка
электрификации удаляются.

Имена пунктов — из таблицы railtype (`name`) и русского словаря (см. D7); подпись самой
настройки — обычные ключи `en.json`/`ru.json`.

### D6. Точки входа пути в расчёт

- `optimize.ts`: фильтры локомотива/вагона — `isPoweredOn`/`isCompatibleWith` вместо
  `base_track_type ===` и `allowElectric`; выбранный railtype приходит через `calc`.
- `consist.ts` (`consistPhysics`/`consistStats`): принимают railtype и считают предел
  скорости и мощность через `vehicleSpeedOn`/`vehiclePowerOn`. Вкладки дохода рейса,
  конструктора и снабжения получают эффект автоматически (единая модель).
- Каталог (`ConsistPage`): показ по `isPoweredOn`/`isCompatibleWith` от общего выбора.

### D7. Русские имена путей — генерируемым словарём, как у грузов

Русских строк у Iron Horse нет вовсе (`src/lang/` — только `english.toml` и
`suppressed_strings.toml`), а ванильные строки игры — прилагательные с падежными
вариантами (`russian.txt:2979-2990`: «Ж/д», «Электрифиц. ж/д», «Монорельсовый»,
«Магнитный»), которые пунктом списка не читаются. Поэтому:

- английские имена берутся из строк набора и игры (`english.toml:675-734`,
  `english.txt:2816-2819`) и кладутся в `meta.railtypes.name`;
- русские — в отдельный генерируемый словарь `railtypes.ru.json` рядом с `cargos.ru.json`,
  который пишет экстрактор русских имён и сверяет `make check-i18n`. Инлайновое поле
  `name_ru` в данных отклонено: оно обошло бы принятый в проекте механизм словарей и его
  проверку на дрейф.
- Ванильные имена в словаре — существительные, собранные из формы игры («Магнитная
  ж/д», а не «Магнитный»): правка формы, не лексики, — тот же случай, что
  `ru_overrides.json`, и она фиксируется там же.
- **`LGVN` и `LGVE` в Iron Horse названы одной и той же строкой** («Dedicated High Speed
  Railway», `english.toml:675` и `:694`). Два неразличимых пункта в списке недопустимы,
  поэтому электрифицированный вариант получает уточнение в обоих языках («… (electrified)»
  / «… (электрифицированная)») — это наша строка интерфейса, а не имя из набора.

## Risks / Trade-offs

- [Маски Iron Horse без нормализации дают пустые каталоги NAAN и MTRO] → D1 добавляет свой
  тип в маски; тест пайплайна на это — обязательная часть задачи, а не факультатив.
- [Кросс-сторовая миграция читает чужие ключи `localStorage` напрямую] → шаг одноразовый и
  покрыт тестом на все три прошлых состояния; при отсутствии или порче чужого ключа выбор
  остаётся дефолтным `RAIL` — деградация без исключения.
- [Лимитов скорости нет ни у одного текущего пути — ветка `min` не покрыта данными] →
  юнит-тесты с синтетическим railtype (лимит ниже предела состава); сценарий спеки
  сформулирован по модели, не по данным.
- [Числа электро-дизелей и HST меняются при том же вводе] → осознанно (см. proposal,
  semver minor в 0.x); эталоны тестов обновляются со сверкой против vendor-источников.
- [Неизвестный лейбл в сторе после смены набора] → нормализация чтения в `'RAIL'`, как
  `normaliseGame()` делает для других настроек.

## Migration Plan

1. Данные: экстракторы (таблицы railtype + нормализация масок) и русский словарь имён,
   `make data`, эталоны `test_known_values.py`, `validate.py`.
2. Движок: `engine/tracktypes.ts`, правки `optimize.ts`/`consist.ts`, тесты формул.
3. Сторы: домен `calc.trackType`, три миграции (D4), кросс-сторовый перенос флажка.
4. UI: `TrackTypeSelect` на четырёх вкладках и в Settings, удаление обоих флажков и
   локального фильтра, ключи подписи.
5. `CHANGELOG.md` `[Unreleased]` с пометкой **BREAKING**.

Откат — revert. Сохранённое состояние прошлых версий переживает откат: миграции только
дописывают выбор пути, а удалённые поля флажка при откате вернутся к своим дефолтам.
