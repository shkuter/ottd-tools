# Design: track-type-axis

## Context

Мотивация — в proposal.md; требования — в спеках change. Технически сейчас:

- `calc.trackType: TrackType` (`engine/settings.ts:236`, союз в `types.ts:12`) — семейство
  `'RAIL'|'NG'|'METRO'|'MONO'|'MAGLEV'`; фильтры в `optimize.ts:294,303` — точное равенство
  `base_track_type === trackType`.
- `allowElectric` — **не URL-параметр, а поле persist-стора**: `state/searchParams.ts:10-23`
  (`DEFAULT_SEARCH_PARAMS`, `searchStorePersist()` `:41-56`, `SEARCH_STORE_VERSION = 1`).
  Второй, независимый экземпляр — у вкладки снабжения (`state/industrySupplyStore.ts:54`,
  контрол `features/industry-supply/IndustrySupplyPage.tsx:137`, прокидывание в
  `features/industry-supply/inputs.ts:16,92`). `URLSearchParams` в `web/src` не используется
  вовсе. Отсекает `isPureElectric()` (`optimize.ts:82`).
- В `trains.json` у каждой из 1648 машин есть `base_track_type`, `track_types` (лейблы),
  `lgv_capable`, `speed_lgv_mph/_internal` и `power_by_source` — **мапа «источник → л.с.»**
  (`{"DIESEL":950,"OHLE":2500}` у `shoebox`; 13 машин с двумя источниками, 21 с
  `lgv_capable`). Из них читается только `power_by_source` — и только в `isPureElectric`.
- В `vanilla_trains.json` — сырой макрос `railtype: 'R'|'C'|'O'|'L'`
  (`extract_vanilla.py:223`); `vanilla.ts:69-74` схлопывает `C` (ELECTRIC) в `'RAIL'`.
- Таблиц самих railtype (лимит, powered/compatible, имя) в данных нет вообще.
- `settingsStore` — persist версии 2 с ветками лесенкой (`version < 1`, `< 2`), новая ветка
  ложится штатно.

Семантика отношений в источниках: маски хранятся **со стороны типа машины**
(`vendor/openttd/src/rail.h:176-181`). Важная тонкость: в NewGRF списки перечисляют
**другие** типы — свой подразумевается и в списке не пишется (`narrow_gauge.py` объявляет
powered `["NAAE"]`, у `metro.py` списки пусты), тогда как ванильная таблица включает свой
тип явно (`railtypes.h:65`: RAIL powered = {RAIL, ELECTRIC}). Приведение к одному виду —
задача экстрактора, см. D1.

## Goals / Non-Goals

**Goals:**

- Таблица railtype в данных каждого набора; выбор пути — лейбл railtype, а не семейство.
- Допуск и числа машин зависят от выбранного пути (powered/compatible, лимит, LGV, мощность
  по источнику тяги).
- Миграции сохранённого состояния во всех трёх сторах без потери смысла выбора.

**Non-Goals:**

- Не менять модель `base_track_type` в данных: семейство остаётся (скорости/вместимости
  Iron Horse заданы по нему, `purchaseKey()` `purchase.ts:24-27` группирует по нему).
- Не трогать физику разгона как таковую — меняются только входы (предел скорости, мощность).

## Decisions

### D1. Таблица railtype живёт в данных своего набора, маски нормализованы

`trains.json.meta.railtypes` (пишет `extract_iron_horse.py`) и
`vanilla_trains.json.meta.railtypes` (пишет `extract_vanilla.py`); `dataset.ts` отдаёт
таблицу активного набора рядом с `activeTrains()`. Запись:

```
{ label, string_id, name, catenary, hidden,
  speed_limit_internal,                     // 0 = нет лимита
  powered: [label...], compatible: [label...],  // со стороны типа машины, СО СВОИМ типом
  lgv: bool, sort }
```

Альтернатива — отдельный `railtypes.json` — отклонена: два экстрактора писали бы в один
файл, и файл пришлось бы согласовывать с включённым набором отдельным кодом.

`catenary` — флаг контактной сети из источников (`RailTypeFlag::Catenary` у игры,
`RAILTYPE_FLAG_CATENARY` у набора). Он решает сразу две задачи: по нему выбирается источник
мощности (D3) и по нему различаются пути, которым набор дал одно имя (D7).

`hidden` — `RAILTYPE_FLAG_HIDDEN`, «нет в меню строительства» (`rail.h`: hiding from
selection). Iron Horse так держит `LGVN`: путь существует, чтобы скоростные машины
оставались совместимы с обычной колеёй, но проложить его нельзя. Такой путь **остаётся в
таблице** — без него рвутся отношения его машин — и **не попадает в выбор**: список выбора
отдаёт `selectableRailtypes(game)`, расчёт по-прежнему работает со всей таблицей
(`activeRailtypes`). Считать маршрут по пути, которого игрок не может построить, значит
обещать числа, которых в его игре не будет.

**Нормализация масок — обязательна, иначе каталог пустеет.** Экстрактор Iron Horse:
(1) отбрасывает legacy-лейблы, которых нет в собственной таблице (`NAAE`, `IHA_`, `IHB_`,
`IHBA`); (2) **добавляет сам тип** в обе маски; (3) достраивает `compatible` до `powered`.
Без второго шага у `NAAN` и `MTRO` маски станут пустыми и по формуле D2 ни одна
узкоколейная машина и ни один поезд метро не окажутся допущены на свой же путь. Третий шаг —
правило самой игры, а не набора: тип, на котором машина питается, она заведомо проезжает
(`newgrf_act0_railtypes.cpp`). Ванильные маски уже включают свой тип — приводим к одному
виду. Тест пайплайна: у каждого типа его собственный лейбл входит в `powered` и в
`compatible`, `powered ⊆ compatible`, и все ссылки масок разрешаются в таблице.

Прочие частности данных:

- Ваниль: лейблы из `rail_type.h:17-20` (`RAIL`, `ELRL`, `MONO`, **`MGLV`** — не `MAGLEV`,
  это имя семейства), маски и `max_speed` из `table/railtypes.h`. `extract_vanilla.py`
  декодирует макрос `p[9]` в лейбл у себя (как уже декодирует `RUNNING_COST_KEYS` и
  `ENGINE_CLASS_KEYS`), наружу сырая буква не выходит. Маппинг в `vanilla.ts` при этом не
  исчезает, а меняет смысл: он больше не декодирует букву, а переводит лейбл пути в
  семейство машины (`ELRL` → `RAIL`), которое остаётся в данных для `purchaseKey()` и
  скоростей Iron Horse.
- Iron Horse: 6 типов из `src/railtypes/*.py`. У `rail` и `rail_electrified_ohle`
  `suppress_for_nml=True` (их определяет игра) и `sort_order = None` — маски и порядок для
  них берутся ванильные. `speed_limit` есть у всех (`railtype.py:17`, по умолчанию 0).

### D2. Допуск машины считается в рантайме по таблице, а не прекомпилируется в машины

Новый чистый модуль `engine/tracktypes.ts`:

- `isPoweredOn(train, railtype, table)` — существует ли `L ∈ train.track_types`, для
  которого `railtype.label ∈ table[L].powered`; `isCompatibleWith` — то же по `compatible`.
  Работает благодаря нормализации D1: у машины на своём же пути отношение выполняется.
- `vehicleSpeedOn(train, railtype)` — `speed_lgv_internal` на `lgv`-пути для
  `lgv_capable`-машин, иначе `speed_internal`; предел состава затем
  `min(..., railtype.speed_limit_internal || ∞)`.
- `poweredOutputOn(train, railtype, table)` — **сколько машина даёт здесь**: ноль, если путь
  её не запитывает, иначе мощность её источника. Это и есть точка, которую спрашивают и
  расчёт, и витрина; ниже неё лежит `vehiclePowerOn(train, railtype)` — «какой источник», без
  вопроса о допуске. Держать гейт в вызывающих местах пробовали — он разъехался с витриной
  дважды, поэтому правило живёт внутри одной функции.

Альтернатива — экстрактор пишет каждой машине готовые `powered_on: [...]` — отклонена:
раздувает 1648 записей данными, выводимыми из таблицы в шесть строк.

Электро-дизель проходит без спецкейса: `track_types = [ELRL, RAIL]`, и `RAIL ∈
powered(RAIL)` даёт допуск на обычный путь, а какой из двух источников считать — решает
`vehiclePowerOn` внутри `poweredOutputOn`.

### D3. Мощность по источнику тяги — из готовой мапы `power_by_source`

`power_by_source` уже лежит в данных мапой «источник → л.с.» (проверено, см. Context) —
извлекать нечего, правок экстрактора не нужно. Источник в Iron Horse —
`schemas.py:509-511` (`power_by_power_source`), дерево переключателей мощности — `:650-684`.

Правило выбора — **иерархия источников набора**, а не «сколько больше»: Iron Horse строит
цепочку переключателей в фиксированном порядке `OHLE > METRO > BATTERY_HYBRID > DIESEL >
STEAM` (`global_constants.py:874`) и сам оговаривает, что порядок и есть правило. Берётся
первый доступный источник этого порядка, где `OHLE` доступен только на пути с `catenary`.
На сегодняшних данных максимум дал бы тот же ответ (единственная пара — `DIESEL + OHLE`, и
OHLE всегда мощнее), но совпадение — не правило: набор вправе выпустить машину, у которой
слабее именно электрическая тяга.

Ванильные `MONORAIL` и `MAGLEV` дописаны в тот же порядок — они реальны, а не гипотетичны, и
у своих машин всегда единственные. Источник, которого в порядке нет вовсе (свой источник
будущего набора), машину тоже не обнуляет: она считается по нему, как считалась бы по
единственному. Обнуление остаётся только там, где ни один источник на этом пути не работает
— электровоз без контактной сети.

### D4. Выбор — `calc.trackType` с доменом лейблов; мигрируют три стора

`CalcSettings.trackType: string` (лейбл railtype), дефолт `'RAIL'`. Участвует в расчёте —
кейс в `settings-effect.test.ts:195` перестраивается с `'NG'` на пару, различимую только
машинами (`RAIL` против `ELRL`); механизм собственной базы кейса (`base`/`baseCalc`,
`:114`) уже есть. `GameSettings` не трогается.

Миграция семейства в лейбл — обычная ветка `settingsStore` (v2 → v3, лесенкой, ранний
выход по текущей версии, тест на состояние каждой прошлой версии): `NG → NAAN`,
`METRO → MTRO`, `MAGLEV → MGLV`; `RAIL` и `MONO` остаются собой.

Перенос флажка сложнее: он сохранён в двух чужих сторах, а выбор пути — один, и **порядок
гидратации сторов не определён** — его задаёт порядок импорта модулей. Миграция внутри
`settingsStore` здесь не годится: если стор вкладки гидратируется первым и перепишет свой
ключ без поля `allowElectric`, переносить будет уже нечего, и пользователь молча потеряет
электрификацию.

Решение — **одноразовый шаг апгрейда вне сторов**: он читает три сырых ключа `localStorage`
(ключи известны, у каждого внутри `state` и `version`), при `trackType === 'RAIL'` и любом
сохранённом `allowElectric === true` записывает выбор `ELRL`, **сам вычищает поля флажка из
обоих ключей вкладок** и помечает себя выполненным.

Где именно он запускается — часть решения, а не деталь. Вызова в теле точки входа
недостаточно: ES-модули выполняют **все импорты до тела модуля**, поэтому любой стор,
который тянется по дереву импортов (`App` → страница подбора → `optimizerStore`),
гидратируется раньше и успевает переписать свой ключ. Поэтому шаг живёт в отдельном модуле
с побочным эффектом — `state/upgradeOnLoad.ts`, — и он **первый импорт** `main.tsx`: порядок
импортов и есть единственная гарантия, которую даёт язык.

Из того же правила следует запрет, который легко нарушить: **модуль апгрейда не импортирует
ни один стор** — даже ради константы с именем ключа. Импорт стора и есть его гидратация, и
она случится раньше переноса; тогда в хранилище окажется новый путь, а в памяти — старый, и
первая же запись настроек затрёт перенос. Ключи и версия схемы поэтому выписаны в модуле
строками, а тесты стерегут их совпадение с настоящими.

Шаги гейтятся **версией**, а не признаком «апгрейд уже запускался»: второй шаг, добавленный
позже, обязан дойти до тех, кто прошёл первый (та же лесенка, что в `migrate` сторов).

Тесты: точка входа импортирует модуль первым; импорт выполняет перенос; перенесённый путь
виден **живому стору**, а не только хранилищу; поздний шаг доходит до прошедших ранний.

Миграции сторов вкладок при этом тоже удаляют поле (v1 → v2) — как подстраховка на случай,
если шаг не отработал вовсе; переносом они не занимаются.

Альтернативы: делать перенос в `migrate` самого `settingsStore` — отклонена по причине
выше (гонка порядка); спросить пользователя баннером — отклонена: у прежнего выбора есть
однозначный смысл, и молчаливый перенос честнее вопроса «чего вы хотели».

### D5. Контрол один, экземпляров четыре

Компонент `TrackTypeField` (`components/`), читает/пишет `settingsStore.calc.trackType`,
ставится в ряд отбора **четырёх** вкладок — подбор, конструктор состава, доход рейса,
снабжение — и в Settings. Локальный `useState`-фильтр `ConsistPage.tsx:57` и оба флажка
электрификации удаляются.

Список пунктов — `selectableRailtypes(game)` (без скрытых, см. D1); имена — из таблицы
railtype и русского словаря (см. D7); подпись самой настройки — обычные ключи
`en.json`/`ru.json`. Правило «незнакомый лейбл читается как `RAIL`» компонент не повторяет,
а берёт у `activeRailtype()`: список обязан показывать тот путь, по которому идёт расчёт.

Ряды вкладок сами дают полю ширину, а строка настроек — ещё и подпись, поэтому у компонента
два узких пропа: `className`/`width` и `withLabel`. Без второго подпись «Тип путей» на
вкладке настроек рисуется дважды — своя у поля и своя у строки.

Сохранённый выбор компонент **читает** через ту же нормализацию и почти никогда не трогает.
Единственное исключение — путь активного набора, который набор скрыл: предложить его нельзя,
и вернуться к нему тоже, поэтому выбор сдвигается на первый доступный. Путь **чужого**
набора так не переписывается: пользователь выбрал его для партии, к которой может
вернуться, — он лишь читается как обычный.

### D6. Точки входа пути в расчёт и в показ

- `optimize.ts`: фильтры локомотива/вагона — `isPoweredOn`/`isCompatibleWith` вместо
  `base_track_type ===` и `allowElectric`; выбранный railtype приходит через `calc`.
- `consist.ts` (`consistPhysics`/`consistStats`): принимают railtype и считают предел
  скорости и мощность через `vehicleSpeedOn`/`vehiclePowerOn`. Вкладки дохода рейса,
  конструктора и снабжения получают эффект автоматически (единая модель).
- Каталог (`ConsistPage`): и отбор, и **числа** — от общего выбора. Отбор идёт через
  `canRunOn()` (одно правило на каталог и оптимизатор: локомотив тянет, вагон едет), а
  колонки мощности и скорости показывают то, что машина даёт на выбранной линии, — иначе
  каталог обещал бы электро-дизелю 2500 л.с. там, где состав из него же посчитан по 950.
  Сортировка читает те же числа, что печатают ячейки, и **прочерк ставится по тому же
  правилу**: где сортировка считает строку «без значения», ячейка рисует «—», а не 0
  (`num(0)` — это строка `"0"`, и `|| '—'` её не ловит).
- Список подбора (`OptimizerPage`) — то же правило: мощность в строке берётся не у поля
  `power_hp`. У 13 электро-дизелей Iron Horse в поле лежит **дизельная** цифра, и строка
  обещала бы 750 л.с. там, где её собственные прибыль и скорость посчитаны по 1900.
- Витрина и расчёт спрашивают **одну функцию** — `poweredOutputOn()`: «сколько машина даёт
  здесь», с гейтом запитанности внутри. Раздельные `isPoweredOn` + `vehiclePowerOn` в
  вызывающих местах уже разъезжались дважды, и это ровно тот случай, когда правило должно
  жить в одном месте, а не повторяться правильно. Половинки ответа —`vehiclePowerOn` и поле
  `power_hp` — за пределами `tracktypes.ts` и `vanilla.ts` не встречаются, и это стережёт
  `__tests__/one-power-figure.test.ts`, читающий сами исходники: сегодняшние наборы не имеют
  машины, на которой половинка дала бы другое число, поэтому обычный тест такую правку
  пропускает — оба прежних расхождения он и пропустил.
- Предупреждение о машинах не по этому пути — общий компонент `StrandedVehicles`, а не часть
  конструктора: тот же состав считает и вкладка дохода, где путь тоже переключается, а нули
  видны не нулями (рейс в сотни дней, на упрощённой модели разгона — бесконечный).
- Вкладка «Партия» пути не выбирает: сейв говорит, какие поезда ходят, но не по чему, а
  калькуляторная настройка описывает чужую партию. Путь выводится из самого состава —
  `trackTypeOfConsist()` берёт первый **строящийся** путь набора, на котором работоспособна
  каждая его часть (порядок таблицы = порядок меню строительства, поэтому дизель не будет
  прочитан как идущий под проводами; скрытый путь исключён — игрок не мог построить то, чего
  нет в меню, хотя отношения по-прежнему читаются по всей таблице). Без этого электрический маршрут импортированной партии считался бы
  с нулевой мощностью. Из того же следует, что вкладка **не сообщает** о расхождении
  настройки пути (`differingSettings`): её прогноз этой настройки не читает, и назвать её
  в списке разошедшихся значило бы отправить пользователя искать дрейф, которого нет.

**Мощность гейтится запитанностью, а не только контактной сетью.** `vehiclePowerOn()`
отвечает на вопрос «каким источником», а не «работает ли машина здесь вообще»: у метровоза
и узкоколейного дизеля источник доступен где угодно, и на обычном пути они выдали бы полную
мощность, хотя не запитаны там ни на что. Игра спрашивает `HasPowerOnRail` прежде, чем
считать мощность (`train_cmd.cpp`), поэтому `consistPhysics` берёт мощность только у машин,
для которых `isPoweredOn` истинно. Из этого же следует и поддержка систем электрификации:
набор, объявивший постоянный и переменный ток разными railtype, различит их масками — без
правок кода расчёта.

Тяговое усилие идёт за мощностью: машина, которая на этом пути не питается, и не тянет —
игра складывает TE только для запитанных частей (`ground_vehicle.cpp`:
`if (current_power > 0)`). Иначе электровоз, оставленный в составе при переключении на
обычный путь, давал бы 0 л.с. и полную тягу, а предупреждение над сводкой обещало бы нули,
которых рядом не видно.

Лимит пути переводится в mph точным отношением (`internalToMphExact`), а не
`internalToMph()`: та функция усекает, как усекает показ в игре, а это число уходит в
физику, где потерянная единица остаётся потерянной.

Лимит пути — свойство состава, а не машины: `topSpeedOn()` отдаёт его только тем, у кого
есть **своя** скорость. Вагон, который своей не заявляет, и на пути с лимитом остаётся без
предела в колонке — иначе каталог придумал бы ему число, которого в данных нет.

**Ключ дедупликации вагонов в `optimize.ts` считается по числам пути, а не по полям.**
Перебор ведётся по одному представителю на группу вагонов, совпадающих во всём, что читает
расчёт; с появлением этой оси расчёт читает мощность и скорость **на выбранном пути**, а не
поля `power_hp`/`speed_*`. Ключ, оставшийся на полях, склеил бы вагоны, которые путь
различает (питаемый от сети против дизельного, обычный против LGV-способного), и перебор
молча потерял бы лучший из них.

### D7. Русские имена путей — генерируемым словарём, как у грузов

Русских строк у Iron Horse нет вовсе (`src/lang/` — только `english.toml` и
`suppressed_strings.toml`), а ванильные строки игры — прилагательные с падежными
вариантами (`russian.txt:2979-2990`: «Ж/д», «Электрифиц. ж/д», «Монорельсовый»,
«Магнитный»), которые пунктом списка не читаются. Поэтому:

- английские имена берутся из строк набора и игры (`english.toml:675-734`,
  `english.txt:2816-2819`) и кладутся в `meta.railtypes.name`;
- русские — в отдельный генерируемый словарь `railtypes.ru.json` рядом с `cargos.ru.json`,
  который пишет экстрактор русских имён и сверяет `make check-i18n`. Инлайновое поле
  `name_ru` в данных отклонено: оно обошло бы принятый в проекте механизм словарей и его
  проверку на дрейф.
- Ванильные имена — существительные («Магнитная ж/д», а не «Магнитный») — задаются
  **у нас**, в `RAILTYPES_WITHOUT_A_SOURCE` рядом с именами путей Iron Horse, а не в
  `ru_overrides.json`. Тот файл по правилу проекта держит только орфографию, регистр и ё
  поверх чужого перевода; «Монорельсовый» → «Монорельсовая ж/д» — это уже собственное
  название, и место ему там, где такие названия объявлены и объяснены. Признак один и тот
  же: строка игры не называет путь сама по себе, потому что ждёт существительного из
  окружающей фразы. Разделение поддержано **порядком источников**: имя из
  `RAILTYPES_WITHOUT_A_SOURCE` идёт первым, а правка в `ru_overrides.json` на тот же
  string_id — ошибка сборки с указанием, где имя править. Молча проигнорировать её нельзя:
  осталась бы запись, которая выглядит работающей.
- **`LGVN` и `LGVE` в Iron Horse названы одной и той же строкой** («Dedicated High Speed
  Railway», `english.toml:675` и `:694`). Два неразличимых пункта в списке недопустимы,
  поэтому пути, разделившие имя, различаются по единственному, чем они и отличаются, —
  контактной сети (`railtypeOptions`); строка уточнения наша, а не из набора. На сегодня
  видно только один из этой пары: `LGVN` скрыт (D1), но правило написано для набора, а не
  для случая.

## Risks / Trade-offs

- [Маски Iron Horse без нормализации дают пустые каталоги NAAN и MTRO] → D1 добавляет свой
  тип в маски; тест пайплайна на это — обязательная часть задачи, а не факультатив.
- [Кросс-сторовая миграция читает чужие ключи `localStorage` напрямую] → шаг одноразовый и
  покрыт тестом на все три прошлых состояния; при отсутствии или порче чужого ключа выбор
  остаётся дефолтным `RAIL` — деградация без исключения.
- [Лимитов скорости нет ни у одного текущего пути — ветка `min` не покрыта данными] →
  юнит-тесты с синтетическим railtype (лимит ниже предела состава); сценарий спеки
  сформулирован по модели, не по данным.
- [Числа электро-дизелей и HST меняются при том же вводе] → осознанно (см. proposal,
  semver minor в 0.x); эталоны тестов обновляются со сверкой против vendor-источников.
- [Неизвестный лейбл в сторе после смены набора] → нормализация чтения в `'RAIL'`, как
  `normaliseGame()` делает для других настроек.

## Migration Plan

1. Данные: экстракторы (таблицы railtype + нормализация масок) и русский словарь имён,
   `make data`, эталоны `test_known_values.py`, `validate.py`.
2. Движок: `engine/tracktypes.ts`, правки `optimize.ts`/`consist.ts`, тесты формул.
3. Сторы: домен `calc.trackType`, три миграции (D4), кросс-сторовый перенос флажка.
4. UI: `TrackTypeField` на четырёх вкладках и в Settings, удаление обоих флажков и
   локального фильтра, ключи подписи.
5. `CHANGELOG.md` `[Unreleased]` с пометкой **BREAKING**.

Откат — revert. Сохранённое состояние прошлых версий переживает откат: миграции только
дописывают выбор пути, а удалённые поля флажка при откате вернутся к своим дефолтам.
