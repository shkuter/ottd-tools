## Context

Мотивация — в `proposal.md`. Здесь состояние, определяющее подход.

- `industries.json` уже содержит по экономикам `accepts` с полем `ratio`, `accept_mode`
  (`all` / `any_2` / `any_3` / `independent`) и `produces`. Правил снабжения в нём нет.
- `accept_mode` оказался производной величиной: `any_3` — это пять входов ratio 3 под потолком
  8. Отдельная ветка расчёта под каждый режим не нужна; поле остаётся полезным для текста в
  интерфейсе.
- `optimize.ts` разделяет цели через `GoalStrategy` — объект, читаемый один раз в начале поиска.
  Третья цель добавляется туда же, без ветвлений по коду перебора.
- `chains.ts` содержит только обход графа цепочек; обратного индекса «груз → принимающие
  предприятия» в приложении нет.
- Интервал между визитами (`pickupIntervalDays`) — та же величина, что промежуток между
  прибытиями к получателю. Второй метрики не заводится (см. `CONTEXT.md`, `Pickup interval`).
- Предусловие: ветки загрузки из `add-loading-wait`. Интервал зависит от режима приказов, и без
  этого change колонка отвечала бы только для одного из них.

Модули `engine/`: новый `supply.ts`; изменяется `optimize.ts`; `waiting.ts` и `trip.ts` уже
дают интервал. Настройки: `GameSettings.dayLengthFactor` участвует косвенно, через интервал;
новых настроек нет.

## Goals / Non-Goals

**Goals:**

- Одна формула конверсии на всю вторичку, без ветвления по `accept_mode`.
- Правила снабжения приходят из пайплайна, чтобы обновление FIRS вскрывалось тестами.
- Колонка и цель пользуются одним модулем — расхождение между ними невозможно.

**Non-Goals:**

- Учёт изменённых игроком параметров NewGRF (пороги пула и бонусы) — берутся значения по
  умолчанию.
- Сводный расчёт по всем входам предприятия — следующий change.
- Моделирование выпуска предприятия во времени.

## Decisions

### Правила снабжения выгружает пайплайн, а не зашивает приложение

В запись предприятия добавляется блок правил снабжения: длина окна в тиках, режим приёма,
пороги и бонусы для накопительного пула. Длина окна одинакова для всех, но выгружается всё
равно — иначе смена константы в FIRS не будет видна ни в диффе данных, ни в тестах.

Альтернатива — константа в коде движка — отвергнута: она нарушает правило репозитория о том, что
игровые значения приходят через экстракторы, и делает обновление FIRS молчаливым.

### Конверсия считается одной формулой, режим приёма остаётся для текста

`конверсия = min(8, Σ ratio поданных входов) / 8`. Все наблюдаемые режимы FIRS следуют из неё.
`accept_mode` сохраняется в данных, но участвует только в формулировке подсказки («нужны любые
три из пяти»), а не в арифметике.

Альтернатива — ветка на режим — отвергнута: она дублирует то, что уже выражено в ratio, и
разъедется при следующем изменении FIRS.

### Пороги пула считаются отдельным расчётом, а не частным случаем конверсии

Пул меряет объём за окно, конверсия — факт подачи. Общего знаменателя нет: у пула два порога и
ступенчатый бонус, у конверсии — доля. Модуль отдаёт разные результаты для разных типов
предприятия, а вызывающий код выбирает по типу получателя.

### Третья цель, а не изменение существующих

Регулярность — вторая ось, но переупорядочивать по ней чужую цель нельзя: пользователь,
выбравший «Прибыль», просил прибыль. Цель `supply` ранжирует лексикографически (конверсия,
затем прибыль), потому что конверсия ступенчата и в одиночку оставила бы десятки равных строк.

Альтернатива — удельная стоимость процента конверсии — отвергнута: она поднимает наверх
варианты, которые до максимума не дотягивают вовсе.

### Обратный индекс строится из данных, а не хранится

Индекс «груз → принимающие предприятия» выводится из `industries.json` при выборе экономики и
кешируется в памяти. Хранить его в данных незачем: он производный, а его расхождение с
`accepts` было бы невидимым.

## Risks / Trade-offs

- **Колонка отвечает про один вход, а конверсия зависит от всех.** → Подсказка явно называет
  остальные входы предприятия и оговаривает, что учтён только выбранный груз. Сводный ответ
  даёт следующий change; до него колонка не должна выглядеть исчерпывающей.
- **Пороги пула — параметры NewGRF, а не константы.** → В данных выгружаются значения по
  умолчанию, в подсказке говорится, из чего они получены. Игрок с изменёнными параметрами
  увидит расхождение; это допущение записывается рядом с числом.
- **Модель предполагает равномерное деление интервала между поездами.** → То же допущение, что
  и в `add-loading-wait`; реальные составы сбиваются в паровозики, поэтому вердикт у отношения
  ровно на единице ненадёжен. Отсюда промежуточная зона вместо резкой границы.
- **Пороги промежуточной зоны выбраны без сверки с игрой.** → Выносятся в именованные
  константы модуля с пометкой, что подлежат проверке в партии; в тестах фиксируется поведение
  границ, а не сами числа.
