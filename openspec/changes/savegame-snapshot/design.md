## Context

См. proposal.md — Why. Сегодня `web/src/savegame/` читает четыре чанка (`PATS`, `NGRF`,
`ECMY`, `DATE`) в воркере и строит предложение настроек. Табличные чанки самоописываются
(`chunks.ts` уже разбирает заголовки полей и вложенные структуры), поэтому расширение —
это список запрашиваемых чанков + экстракторы, а не новый парсер. Модули `engine/*`
изменение не затрагивает; из настроек участвует только уже существующий импорт `PATS`.

## Goals / Non-Goals

**Goals**: слой данных снапшота — чтение чанков, сборка модели, хранение, имена.
**Non-Goals**: UI поверх снапшота (change 2), мосты в расчёты (change 3), не-железнодорожный
транспорт (калькулятор считает поезда; автомобили/суда/самолёты в снапшот не попадают).

## Decisions

- **Сопоставление машин — через `EIDS`**: чанк хранит для каждого индекса пула движков пару
  (GRFID, внутренний id). Для Iron Horse внутренний id — это `base_numeric_id` модели
  (roster.py), поэтому пайплайн экспортирует его в `trains.json` каждой записи каталога
  (`extract_iron_horse.py`, поле `numeric_ids` — по одному id на юнит каждой ливреи, плюс id
  скрытых клонов модели); ванильные машины адресуются фиксированными
  индексами `engine_id` — их уже знает `extract_vanilla.py` (порядок таблиц игры), добавить
  поле явно. Альтернатива «матчить по имени» отвергнута: имена локализуются и дублируются.
- **Читаемые чанки**: `VEHS` (sparse table; поезда: связка состава по `next`, глава по
  флагу front, `engine_type`, груз/загрузка, `profit_this_year`/`last_year`, возраст),
  `ORDL` (списки приказов; общий список = общий индекс у поездов) и `ORDR` — пул приказов
  для сейвов старше версии 354: до `SLV_ORDERS_OWNED_BY_ORDERLIST` (saveload.h:404) приказы
  лежат отдельным пулом и список собирается по ссылке на первый приказ, с 354 — внутри
  `ORDL`; граница импорта (295) ниже, поэтому нужны оба формата, `STNN` (+ `GoodsEntry`:
  `status`, рейтинг, пакеты груза), `CAPA` (пул грузовых пакетов — суммы ожидающего груза
  собираются по ссылкам из `GoodsEntry`), `INDY`, `CITY`, `GRPS`, `PLYR`, `EIDS` и `IIDS`
  (маппинг типов индустрий, той же формы, что `EIDS`, — по нему `indtype` станции
  разрешается в FIRS-индустрию и её суффикс имени; в `industries.json` для этого экспортирован
  `numeric_id`).
  Неизвестные поля/чанки пропускаются как сейчас — по самоописанию таблиц.
- **Что делает воркер**: разбор файла и свёртку сети — грузовые пакеты суммируются там же,
  наружу уходит уже ужатая сеть, а не карта и не пулы. Саму модель снапшота собирает главный
  поток: сопоставление машин каталогу требует каталога, а `trains.json` — 1.4 МБ, и его
  копия в чанке воркера стоила дороже (воркер 1.65 МБ против 35 КБ), чем передача свёрнутой
  сети через `postMessage`. Тяжёлая часть — декомпрессия и обход чанков — осталась вне
  главного потока, ради чего воркер и заводился.
- **Имена городов**: словники English Original не переписываются руками — пайплайн парсит
  `vendor/openttd/src/table/townname.h` в JSON (`town_names.json`), генератор ~50 строк TS
  повторяет `MakeEnglishOriginalTownName` (townname.cpp:247) по сиду. Прочие стили —
  заглушка «Город #N» (id города).
- **Имена без состояния приложения**: генератор городов и резолв суффиксов (`names.ts`)
  не знают ни про локаль, ни про сторы — их тянет сборка снапшота. Локаль-зависимая часть
  (`display.ts`) живёт отдельно: она нужна, чтобы сценарии спеки про имена — заглушка
  чужого стиля, суффикс на языке интерфейса — были проверяемы уже здесь, хотя своих
  экранов у снапшота ещё нет (они в change 2). Разделение заодно держит `zustand`-persist
  на `localStorage` подальше от воркера, где `localStorage` нет.
- **Имена станций**: `string_id` станции → ключ суффикса по карте, которую пайплайн
  собирает из lang-файла игры (`##id`-директивы пинят регион сохранений, поэтому номера
  стабильны между версиями); строки тех же ключей извлекаются на ru/en в словари i18n.
  Индустрия рядом со станцией перебивает `string_id` при **любом** его значении, а не только
  при `STR_SV_STNAME_FALLBACK` (strings.cpp:1755): суффикс берётся из строк FIRS (свойство
  `nearby_station_name` типа индустрии — в движке игры оно становится
  `IndustrySpec::station_name`; русский — из `vendor/firs-ru`, как названия индустрий).
  `{NUM}` шаблона — индекс самой станции, как его передаёт игра (strings.cpp:1767).
  Кастомные имена — строкой из сейва.
- **Индустрия из перехваченного слота**: NewGRF-индустрия, занявшая слот базовой игры,
  регистрируется как override и в маппинг сейва (`IIDS`) не попадает вовсе
  (`newgrf_commons.cpp:218`). Такой тип восстанавливается по набору выпускаемых грузов:
  экономика знает, что производит каждая её индустрия, и совпадение засчитывается только
  когда оно единственное. На партии Londworth так опознаются 7 заводов бытовой техники —
  без этого они и станции, названные их именем, оставались бы безымянными.
- **Рейтинг груза читается только там, где он есть у игры**: `GoodsEntry` хранит
  `INITIAL_STATION_RATING = 175` даже у груза, которого станция никогда не видела, а игра
  прячет его за `HasRating()` — битом `State::Rating` в `status` (station_base.h:184,267).
  Без этого гейта снапшот выдумывал бы рейтинги (на партии Londworth — 6190 записей из 6336)
  и раздувал бы запись в IndexedDB.
- **Хранилище — IndexedDB без зависимостей**: рукописная промис-обёртка (~30 строк), одна
  база, один object store, один ключ `current`; запись `{schemaVersion, fileName, savedAt,
  snapshot}`. Версия ниже текущей → запись удаляется, UI просит файл. `localStorage` не
  подходит по объёму (снапшот большой партии — мегабайты), библиотека `idb` не нужна ради
  одного ключа.
- **Подтверждение импорта — одна функция** (`apply.ts`): она и применяет настройки, и
  сохраняет снапшот, поэтому контракт «один файл, одно подтверждение» проверяется тестом, а
  не только глазами в браузере. В компоненте панели логики подтверждения нет.
- **Снапшот — не zustand-стор**: загружается при старте асинхронно и живёт отдельным
  модулем-хранилищем (`web/src/savegame/snapshotStore.ts`) с подпиской для React;
  в persist-механику `settingsStore` не встраивается (там localStorage и другой ритм).

## Risks / Trade-offs

- [Раскладки JGRPP дрейфуют между сборками] → читать поля по именам из заголовка таблицы,
  неизвестное пропускать; регресс-тесты на реальных сейвах обеих веток.
- [`CAPA` в больших партиях объёмен] → в воркере суммировать счётчики пакетов сразу и
  не держать пул в памяти после сборки снапшота.
- [У типа индустрии нет `nearby_station_name` или перевода] → фолбэк: суффикс по `string_id`,
  а если и его нет — просто имя города;
  тест словарей (`locales.test.ts`) покажет дыры после обновления FIRS.
- [Снапшот в IndexedDB устаревает от игры за минуты] → в записи хранится имя файла и дата
  импорта, UI (change 2) их показывает; это осознанная цена решения «хранить».

## Migration Plan

Чистое дополнение: новые чанки читаются рядом со старыми. Схема снапшота версионируется
(`SNAPSHOT_SCHEMA_VERSION`); запись прошлой версии не мигрируется, а удаляется — UI просит
файл заново. Откат — удаление базы IndexedDB, настроек не касается.
