## Context

Мотивация — `proposal.md`, требования — `specs/`. Здесь только то, что определяет подход.

Текущее устройство, которое приходится учитывать:

- `settingsStore` персистится под ключом `ottd-tools-settings` с `version: 1` и своей
  `migrate`; `merge` кладёт сохранённое поверх дефолтов, поэтому смена значения по умолчанию
  сама по себе до старого пользователя не доходит.
- Год живёт в трёх местах: `CalcSettings.priceYear` (persist настроек), `SearchParams.year`
  (`state/searchParams.ts`, общий начальный набор для `optimizerStore` и
  `industrySupplyStore` — у обоих свой persist **без** версии) и локальный `useState(1950)`
  в каталоге, который вообще не переживает перезагрузку.
- `CalcSettings` целиком попадает в снапшот партии: `snapshotSettings()` кладёт `game` и
  `calc` в запись IndexedDB со своим `schemaVersion`. Любое переименование поля настроек —
  это ещё и миграция снапшота.
- Вложенности в настройках нет ни в разметке, ни в стилях: есть только `.setting-row`,
  `.setting-label`, `.setting-control`, `.settings-group` (`index.css`, `skin.css`).

Расчётные модули не трогаются: год читают из `CalcSettings` только `engine/costs.ts` и
`engine/income.ts` — в `engine/inflation.ts` он приходит аргументом, — а `dataset.ts` берёт
наборы из `GameSettings`. Меняется то, какие значения туда приходят, а не как они считаются.

## Goals / Non-Goals

**Goals:**

- Один источник года на всё приложение, без нового поля и без второй миграции ради имени.
- Один приём вложенности параметров набора, годный и для FIRS, и для Base Costs.
- Миграция, которая меняет ровно два поля и ничего больше.

**Non-Goals:**

- Не переносим год в `GameSettings`: год — допущение расчёта, а не параметр партии из
  Advanced Settings.
- Не трогаем `snapshotSettings()` и `schemaVersion` снапшота.
- Не меняем набор настроек, читаемых из сейва.

## Decisions

### Год остаётся полем `CalcSettings.priceYear`

Поле теперь решает не только цены, но и список покупки, так что имя `priceYear` неточно.
Переименовать напрашивается — и всё же нет: это поле лежит внутри `SnapshotSettings` в
IndexedDB, поэтому переименование тянет бамп `schemaVersion` снапшота и вторую миграцию,
рискующую уже загруженной партией. Цена — неточное имя в одном интерфейсе против миграции
хранилища ради него.

Имя остаётся, смысл фиксируется комментарием у поля и подписью в интерфейсе («год расчёта»,
не «год цен»). Альтернатива — новое поле `year` рядом с `priceYear` — отвергнута: два года в
одном интерфейсе ровно то, от чего заход и избавляется.

### Поля года на вкладках правят настройку напрямую

Поле года остаётся на вкладках подбора, каталога и снабжения — там оно нужно по ходу работы, —
но `value` берёт из `settingsStore`, а `onChange` зовёт `setCalc('priceYear', …)`.
Собственного состояния у поля нет, поэтому расхождению взяться неоткуда.

`SearchParams.year` удаляется из `state/searchParams.ts`, вместе с ним `setYear` из
`optimizerStore` и `industrySupplyStore`; локальный `useState` каталога тоже уходит.

Следствие, принятое осознанно: год каталога начинает переживать перезагрузку, чего раньше не
было. Отдельного решения тут нет — общий год лежит в persist настроек, так что сохраняемость
приходит вместе с ним; оставить каталогу забывчивость можно было бы только вернув ему
собственное состояние, то есть отменив само требование.

Альтернатива — оставить года раздельными, а импорт рассылал бы значение в три места — даёт
расхождение обратно при первой же ручной правке на одной из вкладок.

### Миграция `version: 2` меняет ровно два поля

`migrate` в `settingsStore` дополняется веткой `version < 2`, которая ставит `ironHorse` и
`firs` в `false` независимо от сохранённого.

Здесь ловушка: сейчас `migrate` начинается с раннего выхода `if (version >= 1) return
persisted` (`state/settingsStore.ts:90`), поэтому сохранённое состояние v1 вернётся **до**
любой новой ветки и миграция окажется мёртвой. Ранний выход обязан подняться до
`version >= 2`, а ветки применяться по возрастанию: `version < 1` — разделение множителя
running cost, `version < 2` — выключение наборов. Ветка v1 при этом остаётся прежней, но
перестаёт быть последней. Отличить «согласился с дефолтом» от «выбрал то же
самое» persist не даёт — для него это одно значение, — поэтому выборочная миграция
невозможна, и переписываются оба поля у всех.

Тому, кто играет с наборами, возврат стоит двух переключателей или одной загрузки сейва:
`grfSettings()` в `savegame/import.ts` включает наборы по их ролям в партии.

Оба стора вкладок получают `version: 1` с `migrate`, выбрасывающей осиротевший ключ `year`:
без неё persist вернёт его в объект стора как лишнее поле.

### Вложенность — один класс, а не компонент на каждый набор

`Row` получает признак вложенности, дающий класс-модификатор; параметры набора рендерятся
внутри блока набора. Условие видимости уже стоит у обоих наборов — `game.firs` у экономики,
`game.basecostGrf` у множителей, — и задача перестройки в том, чтобы его не потерять, а не
завести заново.

Оформление — сдвиг и разделительная линия по метрикам скина, токенами `--skin-*`, без
собственных hex: `__tests__/skin-palette.test.ts` ловит вписанный руками цвет, а
`make check-visual` — правило, которое ни с чем не совпало.

Секция NewGRF собирается из трёх одинаковых блоков «переключатель + параметры»; отдельный
`Fieldset` под Base Costs исчезает, его переключатель из `legend` становится обычной строкой.

### Подписи

Ключ `settings.basecostGrf` в обеих локалях получает значение `Base Costs` — набор так зовётся
в игре, собственного перевода у него нет.

Подпись года и его подсказка перестают быть верными: `settings.priceYearHint` сейчас гласит
«Имеет значение только при включённой инфляции», а год теперь решает и список покупки. Обе
строки правятся в обеих локалях — это не косметика, а неверное утверждение в интерфейсе;
`i18n/__tests__/locales.test.ts` поймает пропущенный ключ.

### Существующие кейсы `settings-effect.test.ts` пересматриваются вместе с базой

Кейс ловит настройку, только если эталон отличается от него ровно ею (`CLAUDE.md`). Смена базы
на «наборы выключены» делает кейс `firsEconomy` мёртвым — при выключенном FIRS экономика ни на
что не влияет, — и задевает кейсы `basecost*`. Такие кейсы получают свою базу через `base` /
`baseCalc`, как уже сделано для `inflationFixedDates`. Это не побочная уборка, а условие того,
что файл продолжает делать свою работу.

## Risks / Trade-offs

- **Эталонные числа тестов поедут**: `DEFAULT_GAME_SETTINGS` — база в 25 тестовых файлах, и
  там, где тест молча опирался на подключённый Iron Horse, значения станут ванильными →
  каждое расхождение разбирается отдельно; тест, которому нужен именно Iron
  Horse, получает набор явным аргументом, а не через дефолт. Молча переписанный эталон —
  худший исход этого захода.
- **Новый пользователь не находит вкладку цепочек FIRS**: при выключенном FIRS она скрыта
  (`dataset.ts`) → это осознанное следствие; смягчается тем, что импорт сейва включает наборы
  сам, а переключатели стоят первыми в настройках.
- **Старый пользователь теряет привычный режим** без предупреждения → запись в CHANGELOG с
  `**BREAKING**`; вернуть — два переключателя.
- **Общий год удивит того, кто держал разные года на вкладках** → это и есть цель требования
  «Год расчёта один на всё приложение»; расхождение значений по умолчанию (1938 против 1950)
  показывает, что разные года были не решением, а недосмотром.
- **Год теперь меняет две вещи сразу** (список покупки и цены при инфляции): правка ради
  каталога сдвинет и цены → так же ведёт себя игра, где год один.

## Migration Plan

1. `settingsStore`: `version: 2`; ранний выход поднимается до `version >= 2`, ветки идут по
   возрастанию — сначала прежняя `version < 1`, затем новая `version < 2`. Без этого шага
   миграция мертва: нынешний `if (version >= 1) return persisted` вернул бы состояние v1
   раньше, чем новая ветка получит управление.
2. Сторы вкладок: `version: 1`, миграция выбрасывает `year`.
3. Откат — возврат значений по умолчанию и `version: 1`: сохранённое состояние при этом
   останется с выключенными наборами, поэтому откат чинит новых пользователей, но не тех,
   у кого миграция уже отработала. Это цена осознанной перезаписи, и она принимается.
