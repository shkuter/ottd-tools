## Context

См. proposal.md — Why. Ключ к первым двум пунктам — устройство `translate()` в
`pipeline/extract_firs_ru.py`: строка с префиксом `TTD_` резолвится из локали игры, остальные —
из перевода FIRS. `apply_overrides` работает по словарю FIRS **до** этого выбора, поэтому
половина имён для правок недостижима. Проверка «строка используется» построена на множестве
id, собранном по грузам и предприятиям, — в нём `TTD_*` есть, поэтому запись проходит первую
проверку и падает на второй с неверной причиной.

## Goals / Non-Goals

**Goals:**
- Одинаковые имена в одной экономике невозможно закоммитить: сборка падает.
- Правку можно написать для любого имени, каким бы источником оно ни резолвилось.
- Проверка дрейфа сравнивает то, что генератор выдаёт сейчас, а не то, что было до бампа пина.

**Non-Goals:** см. proposal.md — Non-goals.

## Decisions

**Проверка уникальности — после сборки словаря, по экономикам, а не глобально.** Груз и
предприятие живут в разных пространствах имён, и совпадение «Сталь» (груз) и «Сталелитейный
завод» (предприятие) никого не путает; путает пара объектов одного рода, которые пользователь
видит в одном списке и на одном графе. Поэтому проверяются отдельно грузы и предприятия, и
только внутри одной экономики (`economies.json` → `industry_ids`, `cargo_labels`). Глобальная
проверка дала бы ложные срабатывания на предприятиях, которые FIRS намеренно переименовывает
по экономикам.

**Правки применяются к готовому имени, а не к словарю-источнику.** `apply_overrides` переезжает
за `translate()`: на вход — карта «id объекта → строка id → имя», на выход — та же карта с
применёнными правками. Ключом правки остаётся id строки (`STR_IND_TIMBER_YARD`,
`TTD_STR_INDUSTRY_NAME_SAWMILL`) — он и сейчас записан в `ru_overrides.json`, менять формат
файла не нужно. Проверка «строка используется» остаётся, проверка «значение совпадает с `from`»
теперь сверяется с тем, что реально пришло из своего источника, — отсюда и правильное
сообщение об ошибке.

**Коллизия разводится правкой на стороне игры, а не FIRS.** «Лесопилка» у `sawmill` приходит из
локали OpenTTD (`TTD_STR_INDUSTRY_NAME_SAWMILL`), у `timber_yard` — из FIRS
(`STR_IND_TIMBER_YARD`). Правим FIRS-строку: у `timber_yard` в английском `Timber Yard` —
это склад брёвен, и прежнее «Лесной склад» было точнее. Так лексика игры для `sawmill`
(лесопилка = завод) остаётся нетронутой, а расходится именно то имя, которое FIRS перевёл
неудачно. Альтернатива — править игровое имя — отвергнута: пользователь ищет ванильную
лесопилку в игре по её игровому имени.

**`OPENTTD_REF` пинится тегом релиза, а не коммитом мастера.** Локаль меняется в релизных
ветках редко, тег читается и обновляется осознанно; `vendor_meta()` уже умеет вытаскивать
ревизию из клона, так что `meta.json` получает `openttd` тем же путём, что iron-horse и firs.

**Порядок целей `verify`: `data check-i18n test build`.** После перегенерации `check-i18n`
проверяет ровно то, что должно быть закоммичено, и остаётся сигналом «кто-то правил словари
руками или забыл `make data`». Смежно: `data` получает зависимость `fetch-firs-ru`, чтобы бамп
`FIRS_RU_REF` не собирал словари из старого файла.

**Затрагиваемые модули engine/:** нет — расчёт не меняется.
**Настройки:** не участвуют.

## Risks / Trade-offs

- **Проверка уникальности заваливает сборку на давно живущих данных** → до правки прогнать
  генерацию и посмотреть весь список коллизий; если их окажется больше одной, каждую развести
  правкой поверх источника в том же change (сейчас известна ровно одна).
- **Перенос `apply_overrides` меняет момент применения правок** → существующие записи
  адресуются теми же id строк, а тест на «правка больше не находит свою строку» покрывает
  регресс; после правки словари перегенерируются и сверяются с закоммиченными.
- **Пин `vendor/openttd`** сделает `make fetch` на существующих клонах no-op (директория уже
  есть) → в задачах отдельный шаг: проверить на чистом клоне и, если нужно, зафиксировать в
  README/CLAUDE.md, что смена `OPENTTD_REF` требует удалить `vendor/openttd`.
