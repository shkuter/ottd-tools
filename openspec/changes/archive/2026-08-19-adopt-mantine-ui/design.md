## Context

Мотивация — в proposal.md («Why»). Здесь только то, что определяет подход.

Как устроен интерфейс сейчас:

- `main.tsx` публикует палитру базового набора в CSS-переменные (`applyPalette()` из `skin.ts`:
  `--ottd-<группа>-<оттенок>`, 16 групп по 8 оттенков из `data/opengfx2_palette.json`) и ставит
  `document.documentElement.dataset.skin = 'pixel'`. Скин один и включён всегда.
- `skin.css` (459 строк) начинается с блока токенов `--skin-*` (окно, бевели, кнопки, текст,
  списки, поля, свитчи, деньги) и дальше описывает вид через них; в конце блока токены
  «мостиком» присваиваются базовым переменным темы (`--bg`, `--text`, `--accent`…), на которых
  держится `index.css` (644 строки).
- Правила скина написаны под голые теги (`button`, `select`, `input`, `table`) и под собственные
  классы страниц (`.tab`, `.settings-group`, `.setting-row`, `.chip`, `.stats`).
- Таблица одна — каталог машин в `ConsistPage.tsx` на `@tanstack/react-table`, выдача обрезана
  первыми 400 строками при 1648 машинах в данных.
- График дохода в `RoutePage.tsx` — SVG-путь, собранный руками из точек `incomeCurve()`
  (`engine/income.ts`).
- Граф цепочек FIRS рисует graphviz-wasm, подгружаемый лениво на своей вкладке.
- Компонентных тестов нет: vitest покрывает `engine/`, `state/`, `i18n/`, `dataset`. Регрессию
  вёрстки автотесты не поймают.

Проверенные версии (npm, 19.08.2026): `@mantine/*` 9.5.1 (peer `react` `^19.2.0` — в проекте
19.2.8), `mantine-datatable` 9.4.0 (peer `@mantine/core` `>=9`, `react` `>=19`, опубликован
15.07.2026), `recharts` 3.10.1. `mantine-react-table` не подходит: latest 1.3.4 требует
Mantine 6 + Emotion, бета `2.0.0-beta.9` — Mantine `^7.9`, последняя публикация 17.02.2025.

## Goals / Non-Goals

**Goals:**

- Цвета, шрифты и метрики Mantine выводятся из уже существующих токенов `--skin-*` — второго
  набора цветов не появляется, правка скина остаётся правкой одного блока токенов.
- Каскад решается слоями CSS, а не `!important` и не гонкой специфичности.
- Миграция идёт по вкладке за раз: на каждом шаге приложение целиком работает.

**Non-Goals:**

- Не заводим CSS-модуль на каждый компонент: скин — один плоский слой правил.
- Не переносим настройки из `settingsStore` в состояние форм: движок получает настройки явными
  аргументами, второй источник истины для них недопустим.
- Не трогаем `engine/*` — ни один модуль расчёта (`income`, `physics`, `costs`, `inflation`,
  `units`, `optimize`, `consist`, `settings`, `rating`, `availability`) в этом изменении не
  правится, и `GameSettings` / `CalcSettings` не меняют ни состав, ни семантику. Данные тоже не
  затрагиваются, правок в `pipeline/` нет.

## Decisions

### Р1. Тема выводится из токенов скина через `cssVariablesResolver`

Новый модуль `web/src/theme.ts` рядом со `skin.ts` собирает `createTheme({...})` и
`cssVariablesResolver`. Resolver возвращает переменные Mantine, значениями которых стоят
`var(--skin-*)`: фон и текст корпуса, `--mantine-color-default*` (фон, граница, ховер обычных
элементов), цвет ссылок, цвет ошибки. То есть Mantine читает те же токены, что и скин.

`MantineProvider` получает `forceColorScheme="dark"`: скин один, переключателя нет, а
`forceColorScheme` заодно выключает менеджер цветовой схемы — Mantine не пишет свой ключ в
localStorage и не ставит вторую схему поверх нашей.

Альтернатива — прописать цвета прямо в `theme.colors` и забыть про `--skin-*`. Отвергнута:
тогда цвет живёт в двух местах, а комментарий в `skin.css` («TO RECOLOUR: edit only the token
block») перестаёт быть правдой.

### Р2. Палитра 8 оттенков → кортеж из 10

`MantineColorsTuple` требует минимум 10 значений (проверено по
`lib/core/MantineProvider/theme.types.d.ts:165`), у базового набора их 8 (`SHADES` в `skin.ts`).
`theme.ts` расширяет градиент функцией: крайние оттенки дублируются — `[s0, s0, s1, …, s7, s7]`.
В тему кладём те группы, которые реально нужны компонентам: `grey` (корпус), `yellow` (кнопки,
`primaryColor`), `green` и `red` (свитчи, прибыль/убыток), `darkBlue` (заголовок окна, ссылки).
`primaryShade` подбирается так, чтобы залитая кнопка совпала с `--skin-button`.

### Р3. Каскад — слоями, правила по статическим классам

Импортируем `styles.layer.css`, а не `styles.css` (такой файл есть и у `@mantine/core`, и у
`mantine-datatable` — проверено в пакетах): тогда стили библиотеки лежат в `@layer mantine`.
Первой строкой скина объявляем порядок `@layer mantine, app;` и держим свои правила в
`@layer app` — они выигрывают у библиотеки предсказуемо, независимо от специфичности, и при этом
внутри скина порядок остаётся обычным.

Бевели и метрики задаются правилами по статическим классам Mantine (`.mantine-Button-root`,
`.mantine-Input-input`, `.mantine-Tabs-tab`, `.mantine-Switch-track`, …). `withStaticClasses` в
`MantineProvider` включён по умолчанию, классы — часть публичного API библиотеки.

Альтернатива — задавать вид через `classNames` / `styles` на компонентах или через
`theme.components.X.defaultProps`. Отвергнута для скина: он обязан действовать на всё сразу,
включая контролы внутри `DataTable`, до которых пропсы со страницы не дотягиваются. Для точечных
исключений (например, кнопка «+» в строке каталога) пропсы, наоборот, уместны.

### Р4. Каталог: сортировка остаётся нашей, лимит в 400 строк уходит

`mantine-datatable` не сортирует данные сам — он даёт контролируемые `sortStatus` и
`onSortStatusChange` (проверено по `dist/index.d.ts:730-741`). Значит компаратор переезжает в
`useMemo` внутри `ConsistPage` — ровно то, что сейчас делает `getSortedRowModel`. Колонки
описываются объектами `{accessor, title, render, sortable, textAlign}`, где `title` вычисляется
через `t()` **в момент рендера**: строка внутри мемоизации иначе застрянет на прежнем языке
(правило проекта, оно же в спеке `ui-shell`).

Виртуализации в `mantine-datatable` нет, а машин 1648. Поэтому вместо нынешнего «показываем
первые 400» включаем встроенную пагинацию (`page` / `recordsPerPage` / `totalRecords`): все
машины доступны, а в DOM держится одна страница. Спрайт машины — `pinFirstColumn`, кнопка
добавления — `pinLastColumn`.

Альтернатива — оставить `@tanstack/react-table` и просто отрисовать его через `Table` из
Mantine. Отвергнута по решению пользователя: сортируемые заголовки, пагинация, пустое состояние
и закрепление колонок тогда пришлось бы писать руками ещё раз.

### Р5. График дохода — `LineChart` из `@mantine/charts`

Точки те же: `incomeCurve()` из `engine/income.ts`, аргументы не меняются. Отметка текущего
рейса — `referenceLines` (проп есть в общих типах пакета, `lib/types.d.ts:22`) вместо ручной
`<line>` с `strokeDasharray`. Цвета серии и осей берутся из темы, то есть из тех же `--skin-*`.

`@mantine/charts` тянет `recharts` (~500 КБ до сжатия) и нужен только на вкладке дохода, поэтому
вкладка грузится лениво — так же, как уже сделано с graphviz-wasm на вкладке FIRS.

### Р6. Формы: `@mantine/form` только для локального состояния страниц

`@mantine/form` применяется там, где сейчас россыпь `useState` для нескольких связанных полей:
фильтры каталога (вид, путь, год, груз, поиск) и параметры маршрута. Настройки остаются в
`settingsStore` с persist — см. Non-Goals. Если на шаге фильтров окажется, что выигрыш нулевой,
пакет не ставим: решение принимается на этом шаге, задача в tasks.md это допускает.

### Р7. Постоянные предупреждения — `Alert`, всплывающие — `notifications`

Предупреждение о включённой инфляции и сообщение об ошибке GRF остаются статичным блоком
(`Alert`): по спеке они должны быть видны всё время, пока настройка включена, а всплывающее
уведомление исчезает. `@mantine/notifications` берёт на себя разовые события — «состав очищен»,
«настройки сброшены». `components/Warning.tsx` становится тонкой обёрткой над `Alert` либо
исчезает, если вызовов остаётся два-три.

### Р8. `postcss-preset-mantine` не подключаем

Пресет нужен для миксинов Mantine (`light-dark()`, `rem()`, брейкпоинты) в собственных
CSS-модулях. Мы пишем один плоский слой правил, размеры в скине пиксельные и осознанно не
масштабируются, светлой схемы нет — пресет не даёт ничего, кроме ещё одного конфига в сборке.

## Risks / Trade-offs

- **Регрессию вёрстки не поймают тесты — их для UI нет** → миграция идёт по вкладке за раз, после
  каждой вкладка проверяется в браузере (chrome-devtools) на обоих языках; скриншот до/после.
- **Скин и Mantine перебивают друг друга** → слои CSS (Р3) снимают гонку специфичности; на первом
  же шаге собирается страница-образец со всеми типами контролов, и дальше каждый новый компонент
  сверяется с ней.
- **Бандл вырастет** → `recharts` и `mantine-datatable` грузятся только со своими вкладками
  (ленивый импорт маршрутов), размер `make build` замеряется до и после и попадает в отчёт.
- **`mantine-datatable` — сторонний пакет** → живой (15.07.2026), но риск есть; использование
  заперто в одном файле `ConsistPage.tsx`, откат — вернуть `@tanstack/react-table`.
- **Пагинация вместо «первых 400»** → поведение каталога заметно меняется; это улучшение
  (доступны все 1648 машин), но его надо явно показать пользователю при проверке.
- **Mantine может писать в localStorage свой ключ цветовой схемы** → `forceColorScheme` (Р1)
  отключает менеджер; проверяется вручную — после миграции в хранилище только ключи наших сторов.
- **Строки в мемоизации застревают на старом языке** → заголовки колонок и подписи опций строятся
  функциями `() => t(...)`, локаль остаётся зависимостью `useMemo`; проверка — переключение языка
  на каждой вкладке.

## Migration Plan

1. Провайдер, тема, слои, страница-образец с контролами — приложение ещё на старом UI.
2. Общие компоненты (`Warning`, `Money`, `CargoIcon`, `TrainImage`) и оболочка `App.tsx`
   (шапка, вкладки, подвал).
3. По вкладке: настройки → конструктор составов (вместе с таблицей) → доход рейса (вместе с
   графиком) → оптимизатор → цепочки FIRS. Старые классы `index.css` продолжают действовать для
   ещё не перенесённых страниц.
4. Чистка: удалить осиротевшие правила `index.css` / `skin.css`, снять `@tanstack/react-table` и
   `input-switch-polyfill`.

Откат: изменение целиком внутри `web/`, данные и пайплайн не тронуты — `git revert` возвращает
прежний интерфейс без последствий для сохранённого состояния пользователя.
