## Контекст

Данные Iron Horse: 1648 машин, из них 1449 вагонов. Семейства визуальных вариантов есть
только у вагонов; у движков дублей нет ни одного. Ванильный набор (116 машин) семейств не
имеет вовсе, поэтому группировка применяется к `activeTrains(game)` без ветвления по набору —
на ванили она пустая операция.

Две уже существующие группировки решают разные задачи, и это остаётся так:

| | `optimize.ts` (расчётный профиль) | пункт списка покупки |
|---|---|---|
| ключ | только числа, читаемые формулой | вид, пути, имя, вместимость, длина, дата, вес (+ грузы по умолчанию в режиме без FIRS, п. 1a) |
| имя в ключе | нет | да |
| зачем | ускорить перебор (142 → 14 вагонов под уголь) | список, который читает человек |

## Решения

### 1. Ключ пункта включает вес

`doubtful.ts` сейчас группирует по `kind|track|name|capacity|length|intro`. По всему набору
такой ключ даёт 959 пунктов, и ровно в 6 из них внутри оказываются машины с разным весом:
`Metro Coach` и `Metro Mail Van` трёх поколений, `surface_*` (23 т) против `tube_*` (21 т).
Для чекбокса это терпимо, для каталога — нет: каталог кормит расчёт состава, и представитель
соврал бы на 2 т на вагон. Ключ с весом даёт 965 пунктов.

Проверено на всём наборе: с весом в ключе внутри пунктов **не остаётся ни одного расхождения**
по остальным числам — мощность, ТЭ, скорость, `cost_factor`, `running_cost_factor`,
`loading_speed`, все пять вместимостей, рефит, `model_life`, `vehicle_life`, `dual_headed`.
Поэтому представитель безопасен для любого расчёта, а не только для тех полей, что в ключе.

Альтернатива «два ключа» (широкий для чекбоксов, узкий для каталога) отвергнута: два почти
одинаковых ключа — ровно та ловушка, из-за которой группировка уже написана дважды. Цена
единого ключа — на строке чекбоксов метро появится вторая запись с той же подписью; она
честная, машины действительно разные.

### 1a. Грузы по умолчанию — только там, где их читает расчёт

`canCarryIn` смотрит на `default_cargos` ровно в одном режиме: Iron Horse включён, FIRS
выключен (с FIRS работает рефит, на ванили — свой путь). Внутри пункта это поле расходится у
20 пунктов из 965 — `General Flat Wagon` (`drop_side` возит CSTI/IRON/ZINC, `flat_car` — ALUM),
`Coil Carrier`, `Covered Hopper`, `Silo Wagon`.

Безусловное включение поля в ключ ломает саму цель изменения: один пункт «Coil Carrier» (33 т)
распадается на три записи с одинаковой подписью — covered + tarpaulin, uncovered и
рандомизированный, — то есть возвращается баг, ради которого группировка и делалась (это
поймал тест `doubtful.test.ts`). Поэтому поле входит в ключ по режиму: 965 пунктов с FIRS,
990 без него. Ключ и так зависит от настроек через множитель вместимости, так что зависимость
от `GameSettings` не нова по природе; инвариант однородности проверяется отдельно для каждого
режима своим набором полей.

### 2. Представитель — нерандомизированный, ничьи по идентификатору

Это правило `preferWagon` из `optimize.ts` — при переезде оно зовётся `preferTrain`, потому
что общее для машин любого вида: игра показывает головой группы вариантов
нерандомизированную машину, а идентификатор доигрывает ничью, чтобы выбор не зависел от
порядка машин во входных данных. Оно переезжает в общий модуль, и обе вкладки показывают одну
и ту же машину за один и тот же пункт.

145 пунктов состоят из единственной рандомизированной машины (`bulk_cargo_*_combos_*`) — там
представителем становится она, и это верно: в игре они и есть отдельные пункты списка.

### 3. Схлопывание до фильтров, один раз на набор

Каталог группируется один раз (мемо по `game` и `calc.capacityIndex`), фильтры по виду, путям,
году, грузу и поиску работают уже поверх представителей. Это законно именно из-за инварианта
из п. 1: рефит и `model_life` внутри пункта совпадают, поэтому фильтр не может «разорвать»
пункт, оставив одного члена и убрав другого. Фильтр по грузу в режиме без FIRS смотрит на
`default_cargos` — и законен он ровно потому, что в этом режиме поле входит в ключ (п. 1a). Побочный выигрыш — представитель не прыгает при
смене фильтра, а группировка не пересчитывается на каждый ввод в поиске.

Множитель вместимости берётся из `calc.capacityIndex` (как и вся таблица каталога);
одноимённое поле в `consistStore` не читает никто, кроме самого стора, и в этом изменении не
трогается.

### 4. Инвариант как тест, а не как надежда

Утверждение «внутри пункта все числа расчёта совпадают» верно для текущего набора, но это
свойство данных, а не кода: следующая версия Iron Horse может завести ещё одну пару вроде
surface/tube. Поэтому оно оформляется тестом на реальном `trains.json` — он падает, если
пункт станет неоднородным, и мы узнаём об этом при обновлении набора, а не из кривых чисел у
пользователя. Тест живёт в vitest рядом с ключом: `validate.py` про группировку UI не знает.

## Риски

- **Пользователь ищет вариант по имени и не находит его.** Не реализуется: имена внутри
  семейства одинаковы, поиск идёт по имени, а не по идентификатору.
- **Счётчик в пагинации меняется с 1648 на 965.** Ожидаемо и есть цель изменения; комментарий
  в коде про «~1650 vehicles» обновляется.
- **738 из 965 пунктов всё ещё делят имя с другим пунктом** (поколения, RAIL/NG). Это не дубли:
  различаются годом, весом и ценой, которые в таблице видны колонками.
