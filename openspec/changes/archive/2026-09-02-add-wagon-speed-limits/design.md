## Context

См. `proposal.md` — Why. Текущее состояние, важное для подхода:

- `engine/consist.ts::consistPhysics` уже принимает `GameSettings` и в одном цикле по
  `entries` накапливает `speedLimitMph` / `speedLimitInternal` через `minOf`, а после цикла
  один раз применяет лимит пути (`trackSpeedLimit`). Все машины состава участвуют в минимуме
  безусловно.
- Различитель вагона в данных уже есть: `kind: 'wagon' | 'engine'` (Iron Horse 1449/199,
  ваниль 81/35). Отдельная правка экстрактора не нужна.
- `state/settingsStore.ts` — persist со своим `merge`, который собирает `game` как
  `{ ...DEFAULT_GAME_SETTINGS, ...(p.game ?? {}) }`: новое поле настройки приезжает к старому
  сохранению само, со значением по умолчанию. `state/__tests__/settingsStore.test.ts` это уже
  утверждает — для каждого ключа `DEFAULT_GAME_SETTINGS` на состоянии версии 0.
- `savegame/mapping.ts` держит два списка: `GAME_SETTING_SOURCES` — настройки, которые
  становятся `GameSettings`, и `INFO_SETTINGS` — справочные. `vehicle.wagon_speed_limits`
  сейчас во втором.
- Показанный предел скорости берётся из `speed_internal` данных, а физика считает по
  `mphToInternal` — инвариант проекта, менять его этот change не собирается.
- Сам предел состава показан ровно в одном месте — сводка конструктора
  (`features/consist/ConsistPage.tsx`, `consist.stats.speedLimit`). Колонка скорости в подборе
  — установившаяся скорость гружёного и порожнего состава, а не предел.

## Goals / Non-Goals

**Goals**

- Правило игры воспроизводится там же, где сегодня считается минимум, — одним условием в
  цикле, без второго прохода по составу.
- Источник предела вычисляется из тех же величин, что и сам предел, — в одном месте с ним,
  а не пересчитывается в интерфейсе по данным строки (об остающемся зазоре между показанным
  и посчитанным числом см. Risks).

**Non-Goals** (сверх перечисленных в proposal)

- Не вводится отдельный модуль физики скорости: правило живёт в `consistPhysics`, где уже
  живёт минимум.
- Источник предела не сохраняется в состоянии и не переносится из сейва — это производная
  величина, считается при каждом расчёте.

## Decisions

### Настройка живёт в `GameSettings`

`wagonSpeedLimits: boolean`, значение по умолчанию `true`. Настройка меняет расчёт, значит её
место в `GameSettings`, а не рядом с `currency` / `speedUnit`. Имя поля следует остальным
(`freightTrains`, `gradualLoading`), подпись — из локали игры.

Альтернатива — `CalcSettings` — отпадает: это не допущение калькулятора, а настройка партии,
которую игра сохраняет и которую приносит импорт сейва.

### Миграции persist не нужно

`SETTINGS_VERSION` не поднимается и ступень лесенки не добавляется: `merge` стора уже
подмешивает `DEFAULT_GAME_SETTINGS` под сохранённый `game`, поэтому у существующего
пользователя поле появляется со значением `true` — тем самым, при котором его числа не
меняются. Ступень миграции здесь была бы обрядом: она проставляла бы ровно то, что и так
проставляет `merge`.

Лесенка миграций нужна другому — значению, которое надо **пересчитать** из старого (так
делали `trackType` и `trainSet`). Здесь пересчитывать нечего.

### Правило минимума: одно условие в цикле

В цикле по `entries` предел машины участвует в `minOf`, если `train.kind !== 'wagon'` **или**
`game.wagonSpeedLimits`. Это буквальный перенос `train_cmd.cpp:185`. Машина без предела
(`speed.mph == null`) не участвует и сейчас — «без предела» и так не ноль.

Лимит пути остаётся за циклом и настройкой не гейтится: он свойство пути, а не машин.

### Источник предела: категория, без которой предел был бы выше

`consistPhysics` возвращает рядом с `speedLimitInternal` одну производную:
`speedLimitSource: 'engine' | 'wagon' | 'track' | null`. Минимум считается по трём кандидатам
(минимум по не-вагонам, минимум по вагонам — только когда настройка включена, лимит пути).
Источник — та категория, чей кандидат строго меньше двух других; при ничьей `null`, и
уточнение не показывается.

Определение через «строго меньше» выбрано вместо «первый по списку приоритетов»: приоритет
при равенстве — произвол, который пришлось бы объяснять пользователю, а при ничьей
объяснять и правда нечего.

Отдельного флага для пометки строки подбора не заводится: пометка — это и есть
`speedLimitSource === 'wagon'`. Второе поле рядом с первым разъехалось бы с ним при первой
правке, а случай «вагоны медленнее локомотива, но связывает путь» пометки и не заслуживает:
скорость держит путь, и другие вагоны её не поднимут.

Альтернатива — считать источник в UI по данным строки — отпадает: UI пришлось бы повторить
логику минимума, включая ветку LGV и настройку, и она разъехалась бы с физикой при первой же
правке.

### Импорт сейва: запись переезжает между списками

`vehicle.wagon_speed_limits` удаляется из `INFO_SETTINGS` и добавляется в
`GAME_SETTING_SOURCES` как `read: (v) => ({ wagonSpeedLimits: v !== 0 })` — той же формы, что
соседние флаги.

«Остальной путь работает сам» — неправда, и на этом уже обожглись: настройку знают **три**
списка, и пропуск любого тихо ломает свою часть. `GAME_SETTING_SOURCES` (`mapping.ts`) читает
значение из файла, `SETTING_LABEL_KEYS` (`features/savegame/settingNames.ts`) даёт ей подпись,
а `GAME_LABELS` (`savegame/diff.ts`) решает, попадёт ли расхождение в список различий: без
записи там настройка применяется молча, ничего не спросив у игрока. Из трёх только второй
охраняется типом (`Record<SettingKey, string>` не соберётся без записи) — остальные два
проверяются тестом.

## Risks / Trade-offs

- **Кейс в `settings-effect.test.ts` держится на том, каким окажется победитель поиска.**
  Своя база (`base`) ему не нужна и не помогла бы: базой задаются настройки эталона, а состав
  выбирает оптимизатор. Кейс утверждает `changed !== reference`, поэтому состав без медленных
  вагонов даст не молчаливый проход, а красный тест — то есть сигнал, а не пропуск. Страховка
  от такого дня — отдельный тест на конкретной паре (локомотив 120, вагоны 45), который не
  зависит от того, кого выберет поиск.
- **На ванильном наборе настройка не наблюдаема** (у вагонов нет пределов вовсе) → это не
  дефект, но тест обязан брать Iron Horse, а подсказка об источнике на ванили просто не
  появится.
- **Уточнение разойдётся с показанным числом**, если считать источник по `speed_internal`, а
  минимум — по `mphToInternal` → источник считается внутри `consistPhysics` из тех же
  величин, что и `speedLimitInternal`. Обратный случай остаётся: два кандидата, различающиеся
  на единицу внутренней скорости, показываются пользователю одним и тем же числом, и
  уточнение назовёт источник там, где глазами разницы нет. Это следствие инварианта
  (показываем из `speed_internal`, считаем по `mphToInternal`), а не этого решения; ломать
  инвариант ради подписи не стоит.
- **Уточнение об источнике попадёт туда, где показан не предел** → в подборе показана
  установившаяся скорость, а не предел, поэтому источник туда не идёт; там живёт только
  пометка строки.
- **Пометка «локомотив быстрее вагонов» превратится в шум**, если показывать её на каждой
  строке подбора, где вагон хоть немного медленнее → пометка привязана к тому же условию, что
  и источник `'wagon'`: пределы должны реально расходиться.

## Migration Plan

Отдельного шага выкатки нет: SPA статическая, миграции состояния не требуется (см. решение
выше). Откат безопасен в обе стороны: старая сборка не знает поля и считает как раньше,
новая подставляет ему значение по умолчанию.
