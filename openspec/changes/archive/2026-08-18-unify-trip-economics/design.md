## Context

Оптимизатор в `engine/optimize.ts` (`evaluate`) уже содержит полную модель рейса; вкладка
«Доход рейса» (`features/route/RoutePage.tsx`, блок `profit`) повторяет её упрощённо внутри
компонента. Различия:

| | Оптимизатор | Route income |
|---|---|---|
| Порожнее плечо | своя скорость (`consistPhysics` без груза) | `days * 2` |
| Стоянка | по типу вагона (один тип) | max по вагонам состава |
| Ограничение производством | да (`cargoPerTrip`) | нет |
| Субсидия | да | нет |
| Ручное время рейса | нет | да (`route.manualDays`) |

Стоянки на самом деле не различаются: в оптимизаторе один тип вагонов, и «max по вагонам»
даёт то же самое. Реальное расхождение — порожнее плечо.

## Goals / Non-Goals

**Goals:**
- Одна функция `tripEconomics()` в новом `engine/trip.ts`; обе вкладки — её потребители.
- Оптимизатор возвращает ровно те же числа, что до change (сверка снимком).
- Ручное время рейса на вкладке продолжает работать.

**Non-Goals:**
- Изменение модели (см. proposal — Non-goals).
- Перенос графика оплаты и остальной логики `RoutePage` в движок — следующий change.

## Decisions

**Модель оптимизатора становится общей, а не модель вкладки.** Она полнее (порожнее плечо,
производство, субсидия), покрыта тестами и уже сравнивалась пользователем с игрой в работе.
Альтернатива — оставить `days * 2` — отброшена: она заведомо грубее физики, которая в проекте
уже посчитана.

**Ручное время задаёт гружёное плечо, порожнее масштабируется по отношению скоростей.**
Альтернативы: (а) считать порожнее тоже равным ручному — возвращает старую грубость;
(б) игнорировать ручной ввод в прибыли — ломает сценарий «я знаю, сколько едет мой поезд».
Масштабирование сохраняет и ввод пользователя, и модель.

**Затрагиваемые модули engine/:** новый `trip.ts`; `optimize.ts` (тонкий вызов, остаётся
перебор, отбор, рейтинг станции и `trainsNeeded`); `consist.ts`, `costs.ts`, `income.ts`,
`physics.ts`, `units.ts`, `settings.ts` — как зависимости без правок.

**Настройки, участвующие в расчёте:** `GameSettings` — `gradualLoading`, `accelerationModel`,
`freightTrains`, `jgrpp`, `dayLengthFactor`, `timekeeping`, `minutesPerYear`,
`vehicleCostsWhenStopped`, `cargoAgingRate`, `paymentAlgorithm`, `subsidyMultiplier`, все
ценовые (через `pricing`); `CalcSettings` — `capacityIndex`, `priceYear`.

**Рейтинг станции и `trainsNeeded` остаются в оптимизаторе.** Они нужны только там (вкладка
рейса не знает про производство), а `tripEconomics()` даёт им вход — `roundTripDays`,
`tripsPerYear`, `capacity`. `cargoPerTrip` вычисляется в оптимизаторе и передаётся параметром.

## Risks / Trade-offs

- **Двойной вызов `consistPhysics` в цикле перебора** → так уже сейчас; `tripEconomics()` не
  добавляет вызовов. Проверить, что время `optimizeConsists` не выросло заметно.
- **Тонкая разница округлений при переносе** → снимок 96 строк × 4 набора настроек до/после,
  сравнение до 6 знаков.
- **Пользователь заметит изменение чисел на вкладке рейса** → запись в CHANGELOG и major.

## Open Questions

Сверено с `vendor/openttd/src/economy.cpp` (`LoadUnloadVehicle`, строки ~1607–1917;
`gradual_loading_wait_time = {40, 20, 10, 20}` на ~1847): модель «вагоны параллельно, слайс
поезда 40 тиков, разгрузка и погрузка одного вагона последовательно» — верна. Отложено на этап
сверки формул (меняют числа, здесь не трогаем):

- Игра обходит **весь** состав, включая локомотивы с собственной вместимостью (railcar):
  такой локомотив тоже грузится и может удлинить стоянку. Сейчас стоянка считается только по
  вагонам.
- Стоянка начинается с `load_unload_ticks = 1` — фактическое время `1 + 40·N`, а не `40·N`.
- `station_length_loading_penalty`: поезд длиннее платформы грузится вдвое дольше плюс
  `10 · overhang` тиков за слайс. Оптимизатор ограничивает длину станцией, вкладка рейса —
  нет.
- Порожний поезд на конечной без выгрузки стоит ~1 тик; сейчас на обоих концах одинаково.
