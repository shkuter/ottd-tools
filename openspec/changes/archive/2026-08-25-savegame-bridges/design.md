# Design: мосты из партии в расчёты

## Context

Мотивация — см. proposal.md «Why»; требования — спеки `savegame-bridges` и дельта
`savegame-snapshot`. Что уже есть:

- `features/savegame/routeRows.ts` строит `RouteRow` с прогнозом и его блокером
  (`ForecastBlocker`) — карточка маршрута уже знает, когда модель применима, и называет
  причину ключами `game.blocker.*`.
- Снапшот несёт `SnapshotRoute.legTiles` (дистанции плеч), `SnapshotTrain.consist`
  (записи каталога id+count), `SnapshotStation.goods` (рейтинги по грузам),
  `SnapshotIndustry.produced`. Привязки станция → индустрии нет; в сырье есть опорный тайл
  станции (`stnn.ts`), у индустрии (`indy.ts`) нет ни тайла, ни размера.
- Сторы-приёмники: `routeStore` (cargoLabel, distanceTiles, amount, manualDays,
  productionPerMonth, waitForFullLoad), `optimizerStore` (cargoLabel, distanceTiles,
  productionPerMonth, …), `consistStore` (entries id+count, cargoLabel). Все под persist.
- Вкладки: `/income` (RoutePage читает routeStore + consistStore), `/optimizer`;
  навигация — react-router.
- `SNAPSHOT_SCHEMA_VERSION = 2` (в `snapshotStore.ts`); рекорд другой версии дропается без
  миграции, вкладка просит файл заново (механизм части 1).

Термины — по `CONTEXT.md`: **поток** (flow) — выпуск источника, отдаваемый станции, единиц
за экономический месяц; это `productionPerMonth` сторов. «Supply» в глоссарии занято
приёмкой FIRS (окно поставок), поэтому здесь не используется.

## Goals / Non-Goals

**Goals**

- Причина недоступности моста берётся из тех же предикатов, что и прогноз, — без второго
  набора правил.
- Мост — чистые функции, тестируемые без React (как `routeRows.ts`).
- Привязка станция → поставщики считается один раз при разборе, как `legTiles`.

**Non-Goals**

- См. proposal «Non-goals». Дополнительно на уровне дизайна: никакого нового стора для
  мостов — пометка происхождения живёт в существующих сторах-приёмниках; никаких изменений
  движка (`engine/*`) — мосты только заполняют его существующие входы.

## Участие engine/ и настроек

Модули `engine/` этим изменением **не правятся**. Мост пишет во входы, которые уже
потребляют `engine/trip.ts` (`routeWithFlow`, `tripEconomics`), `engine/consist.ts`
(`consistStats`), `engine/income.ts` (`cargoPaymentRate`) и `engine/optimize.ts` — через
сторы, как это делает пользователь руками.

Настройки в расчёт мостом **не переносятся** и не меняются: `GameSettings`/`CalcSettings`
вкладки-приёмника остаются из `settingsStore`. Новых настроек изменение не вводит, поэтому
кейса в `engine/__tests__/settings-effect.test.ts` не прибавляется. Расхождение это
осознанное: карточка партии считает прогноз по `SnapshotSettings` (настройки партии),
приёмник — по текущим; спека фиксирует это отдельным сценарием.

Настройки читаются в двух местах, и оба про выбор набора машин, а не про формулы: мост
оживляет состав по `activeTrains(settings.game)` (набор той партии, из которой он снят), а
вкладка-приёмник считает только по машинам своего активного набора (`activeEntries`,
Decision 4) — иначе к ванильной машине применились бы шифты Iron Horse.

## Decisions

### 1. Причина моста — свой порядок тех же предикатов

`forecastBlocker` (`routeRows.ts:141`) упорядочен под прогноз: `multiStop` проверяется
**раньше** груза и состава. Мосту этот порядок не подходит — число остановок определяет
объём переноса, а не доступность, поэтому у кольцевого маршрута с разнородным парком
`row.blocker` назвал бы `multiStop`, а мешает парк.

Решение: `routeRows.ts` отдаёт предикаты, а не только готовый блокер — единый состав
(`row.consist === null` → `mixedFleet`), опознанность (`entries === null` →
`unmatchedVehicle`), груз (`row.cargo === null` → `noCargo`). Мост складывает из них свою
причину в своём порядке; словарь причин (`ForecastBlocker`, ключи `game.blocker.*`) — тот
же, новых ключей причин не заводится. Так «одна логика» держится на общих предикатах, а не
на общем их порядке.

Альтернатива — взять `row.blocker` как есть — отклонена ровно из-за порядка: причина была бы
ложной. Альтернатива «своя независимая проверка в кнопке» отклонена: два набора правил
разъедутся при следующем блокере.

### 2. Привязка станция → поставщики: площадки при разборе

Полного прямоугольника станции в сейве **нет**: `StationRect rect` помечен `NOSAVE`
(`vendor/openttd/src/base_station_base.h:84`) и пересобирается игрой на загрузке. Зато
сохраняется ж/д площадка — она же и нужна, поезда грузятся на ней:

- `extract/stnn.ts` читает `train_station.tile`, `train_station.w`, `train_station.h`
  (`saveload/station_sl.cpp:459-465`; JGRPP — там же, :593-595). Станция без ж/д части
  оставляет площадку пустой.
- `extract/indy.ts` читает `location.tile`, `location.w`, `location.h`
  (`saveload/industry_sl.cpp:152-155`).
- `snapshot.ts`: поставщик станции = площадка индустрии пересекает площадку станции,
  расширенную на радиус охвата. Радиус — 4 (`CA_TRAIN`, `vendor/openttd/src/station_type.h:117`,
  равен `CA_UNMODIFIED` :120) плюс JGRPP-настройка `station.catchment_increase` из настроек
  сейва, когда она там есть (дефолт 0).
- Хранение: `SnapshotStation.supplierIds: number[]` (id индустрий снапшота). Поток по грузу
  считается на вкладке из `industries.produced` — снапшот держит связь, не произведение:
  груз маршрута определяется только на вкладке (`routeCargo`), и хранить «поток по всем
  грузам» значило бы дублировать produced.
- `SNAPSHOT_SCHEMA_VERSION` (в `snapshotStore.ts`) → 3.

Альтернатива «манхэттен от опорного тайла с порогом» отклонена: опорный тайл — северный
угол, длинная станция дотягивается охватом много дальше любого фиксированного порога, а
широкий порог захватывает чужие индустрии. Прямоугольник + радиус — то, что игра и делает,
с точностью до типов тайлов (названо приближением в спеке).

### 3. Мост — чистые функции + применение в сторы

Новый модуль `features/savegame/bridge.ts`. Имена — «откуда → куда», единообразно:

- `routeToIncome(row, snapshot)` → перенос целиком или «состав и груз», либо причина;
- `routeToOptimizer(row, snapshot)` → груз, дистанция и поток, либо причина;
- `industryToOptimizer(produced)` → груз и его производство за месяц (какая это индустрия,
  нужно только пометке, не расчёту).

Станция погрузки и её поток считаются здесь (по спеке: рейтинг груза → станция погрузки;
сумма produced поставщиков). Применение — отдельная функция, зовущая сеттеры сторов
(`useConsistStore.getState()`… вне React), затем `navigate('/income' | '/optimizer')`.
Компоненты логики переноса не содержат.

Объём перевозки (`routeStore.amount`) = `forecast.capacity` — то самое число, по которому
карточка считала прогноз. Пересчёт по текущим настройкам не нужен: поле редактируемое,
а нижняя часть вкладки и так считает состав по текущим настройкам.

`manualDays` при полном мосте пишется в `null` («от состава») — иначе на вкладке останется
ручное время от прошлого расчёта, и перенесённый состав посчитается с чужим временем.

### 4. Состав переносится записями активного набора

Он же и отсеивается при чтении: состав переживает смену набора в localStorage, а машина
чужого набора, посчитанная с `activeTrainsMeta` текущих настроек, — это чужие
basecost-шифты, то есть неверные деньги. Поэтому вкладки расчёта берут из стора только то,
что активный набор знает (`inActiveSet`), как экономика поступает с чужим грузом (ADR-0002).


`consistStore` оживляет id через `trainById` (`dataset.ts:25`) — а это **только Iron Horse**;
ванильного каталога в этой карте нет, и `add()` неизвестный id молча отбрасывает. Мост
ванильной партии так потерял бы состав целиком.

Решение: мост кладёт в стор готовые `ConsistEntry` (машина + count), взяв каталог из
`activeTrains(settings.game)` — как это уже делает `routeRows.ts:92`. Для этого
`consistStore` получает `setEntries(entries)`; заодно его persist-`merge` учится оживлять
id обоих наборов (сейчас ванильный состав не пережил бы перезагрузку — проверить это на
вкладке конструктора отдельно, до правки моста).

### 5. Пометка происхождения — сравнение значений, не флаг в сеттерах

В `routeStore` и `optimizerStore` — верхнее поле `prefillOrigin: PrefillOrigin<V> | null`
(persist бесплатно), где `PrefillOrigin<V> = { source: 'route' | 'industry'; label: string;
values: Partial<V> }`, а `V` — набор полей своей вкладки (`RoutePrefill`,
`OptimizerPrefill`); для полного моста в «Доход рейса» туда входит и состав как id+count.
`source` нужен потому, что в оптимизатор ведут два разных моста, и пометка «из маршрута»
для индустрии была бы неправдой. Вкладка показывает пометку, только если текущие значения
равны `values`; сравнение — своя функция, поле за полем.

Правка любого перенесённого поля меняет значения — пометка гаснет сама, **ни один сеттер не
трогается** и межсторной связи нет. Возврат значения руками возвращает и пометку: это
честно (на вкладке снова ровно то, что дал маршрут) и зафиксировано сценарием спеки.
Альтернатива «гасить в сеттерах» отклонена: пришлось бы патчить сеттеры двух-трёх сторов и
связывать `consistStore` с `routeStore`. Альтернатива «отпечаток строкой JSON» отклонена:
типизированный набор переживает переименование поля и читается в тестах.

`label` — готовая строка («Углевоз — Электростанция», имя индустрии) на языке момента
перехода; не перерисовывается при смене языка — приемлемо для эфемерной пометки, не тащим
id снапшота в сторы расчёта.

### 6. Строка уносится стрелкой, значение — кликом по значению

Форма перехода берётся из того, что переносится, а не из того, на какой он вкладке. Правило
уже задано таблицей оптимизатора (`ActionIcon.btn-add` со стрелкой в последней колонке
уносит строку в «Доход рейса») и распространяется на новые места:

- **Строка целиком** → стрелка в последней колонке. У маршрута это переход в «Доход рейса»:
  переносится весь рейс — состав, плечо, объём, поток. Недоступная стрелка остаётся на месте
  и помечается `aria-disabled`, а не `disabled`: настоящий `disabled` выпадает из обхода
  клавиатурой, и причина стала бы доступна только мышью. Причина живёт в подсказке и в
  доступном имени — и это единственное честное место для неё: в колонке прогноза у
  кольцевого маршрута с разнородным парком стоит другая причина (`multiStop` против
  `mixedFleet`), потому что прогноз и мост спотыкаются о разное.
- **Одно значение строки** → ссылка на самом значении (`btn-link cargo-bridge`,
  общий компонент `CargoBridgeLink`). Груз ведёт в «Лучший поезд» и в списке маршрутов, и в
  списке предприятий: у предприятия грузов в строке несколько, и стрелка в колонке не
  сказала бы, о котором речь. Ссылкой становится только груз активного набора — у чужого
  нет ставки оплаты, и переход подменил бы его другим; такой груз остаётся текстом. Там, где
  груза нет вовсе, прочерк несёт подсказку с причиной, а не молчит.

Ссылка инлайновая: `display: flex` на строке груза разбил бы её текст на отдельные элементы
и добавил бы лишний пробел в соседнюю колонку («96 (67%)»). Клик по ссылке и по стрелке
останавливает всплытие — иначе он же раскрывал бы строку маршрута.

Первый заход был другим — две кнопки с подписями в развороте маршрута и кнопка-стрелка в
ячейке груза, — и он развалился на двух проверках: в развороте кнопки нашлись не сразу, а
две стрелки подряд в строке (`→` и `⇥`) читались как один значок.

## Risks / Trade-offs

- [Имена полей `train_station.*` / `location.*` в table-заголовках чанков отличаются между
  OpenTTD и JGRPP или между поддерживаемыми версиями] → сами дескрипторы сверены в обеих
  ветках, но в table-заголовке имена приходят из сейва; тесты на реальных фикстурах
  (`web/src/savegame/__tests__`, обе ветки уже там); при отсутствии полей привязка пустая
  по спеке, разбор не падает.
- [Прямоугольник переоценивает охват Г-образных станций — лишняя шахта в поставщиках] →
  названо приближением в спеке; поток на вкладке-приёмнике редактируем; занижения не бывает.
- [Станция, у которой груз принимает не ж/д часть (док рядом с ж/д), получит поставщиков по
  ж/д площадке] → для мостов это и нужно: считается плечо поезда.
- [Числа вкладки-приёмника расходятся с прогнозом карточки при изменённых настройках] →
  осознанно: Non-goal переноса настроек; сценарий в спеке фиксирует поведение.
- [`consistStore` мог быть сломан для ванильного набора и до мостов] → отдельная проверка в
  задачах перед правкой; если так, чинится там же, где мост (иначе мост «не работает» по
  чужой причине).

## Migration Plan

1. Бамп `SNAPSHOT_SCHEMA_VERSION` 2 → 3 в том же коммите, что расширение модели.
2. Старые снапшоты дропаются штатным механизмом части 1 (вкладка просит импортировать сейв
   заново) — кода миграции нет по устройству хранилища.
3. Откат — git revert: версия вернётся к 2, снапшот v3 дропнется тем же сравнением
   «версия не равна текущей».
